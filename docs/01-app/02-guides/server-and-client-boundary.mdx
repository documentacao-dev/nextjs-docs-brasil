React Server Components (RSC) dividem uma árvore de componentes entre dois grafos de módulos, o do servidor e o do cliente. Essa fronteira determina onde o código do componente roda e se esse código é enviado ao navegador. O RSC mantém os Server Components exclusivamente no servidor e reserva os Client Components para a UI interativa. Os dois tipos compõem uma única árvore, que o servidor renderiza no [RSC Payload](/docs/app/glossary#rsc-payload), uma descrição serializada da UI que carrega referências aos Client Components contidos nela.

Antes do RSC, os componentes React seguiam o que o RSC agora chama de modelo de Client Component. O React podia renderizar esses componentes em HTML no servidor, mas o mesmo código também era enviado ao navegador para [hidratar](https://react.dev/reference/react-dom/client/hydrateRoot#hydrating-server-rendered-html) esse HTML. A hidratação tornava o HTML inicial interativo e exigia que o componente produzisse a mesma saída no servidor e no navegador. Apps renderizados inteiramente no cliente podiam, em vez disso, começar com uma shell vazia e montar a árvore de componentes no navegador.

```txt
Server Component
├─ Server Component
└─ Client Component
   └─ Client Component
```

O módulo de cada componente pertence ao [grafo de módulos](/docs/app/glossary#module-graph) do servidor, ao grafo de módulos do cliente ou a ambos. O Next.js compila separadamente, para cada ambiente, um módulo usado pelos dois grafos.

Durante a renderização, o grafo do servidor produz referências aos Client Components e serializa as props passadas a eles. O grafo do cliente não importa o grafo do servidor. Ele recebe as referências e as props serializadas pelo RSC Payload.

## Ambientes de renderização \{#rendering-environments}

Os nomes dos componentes sugerem uma divisão clara entre servidor e navegador, mas a renderização acontece nos dois lugares. No servidor, a árvore de Server Components produz o RSC Payload. O Next.js usa o payload e os Client Components para renderizar HTML durante o build ou ao processar uma requisição.

Ao decidir onde um componente roda, considere tanto a renderização dele no servidor quanto se o código dele roda no navegador:

|                      | No servidor | No navegador |
| -------------------- | ----------- | ------------ |
| **Server Component** | Sim         | Não          |
| **Client Component** | Sim         | Sim          |

A palavra "Client" indica que um Client Component também roda no navegador, além da renderização no servidor.

Em uma visita direta, o Client Component a seguir é renderizado no servidor e, de novo, no navegador durante a hidratação. O log dele aparece no terminal e no console do navegador. Em uma navegação no cliente, o servidor envia o RSC Payload, e o componente é renderizado no navegador, sem HTML renderizado no servidor.

```tsx filename="app/hello.tsx" switcher
'use client'

export default function Hello() {
  console.log('Hello rendered') // on a direct visit: server, then browser
  return <p>Hello</p>
}
```

```jsx filename="app/hello.js" switcher
'use client'

export default function Hello() {
  console.log('Hello rendered') // on a direct visit: server, then browser
  return <p>Hello</p>
}
```

Renderizar um Client Component no servidor produz HTML, mas o componente continua sendo um Client Component.

Renderizar Client Components em HTML é anterior ao RSC. Dependendo da rota, o Next.js pode gerar ou regenerar o HTML:

- No build, com [Static Site Generation (SSG)](/docs/app/glossary#prerendering).
- Após o build, com [Regeneração Estática Incremental (ISR)](/docs/app/glossary#incremental-static-regeneration-isr).
- Para cada requisição, com Server Rendering (SSR).

O RSC é um processo separado que mantém o código dos Server Components no servidor e emite o RSC Payload, em vez de enviar esse código. "Server-rendered" descreve como o Next.js produziu o HTML. "Server Component" descreve onde o código do componente roda e se esse código é enviado ao navegador.

> **Server Components e SEO**
>
> Um crawler que lê apenas HTML vê a primeira resposta e não executa nenhum do seu JavaScript. Tanto os Server quanto os Client Components contribuem com HTML para essa resposta.
>
> O SEO depende de a renderização no servidor alcançar o conteúdo. Conteúdo que depende de uma interação do usuário ou de um evento não aparece no HTML disponível para um crawler que não executa JavaScript.

Veja [Filosofia de renderização](/docs/app/guides/rendering-philosophy) para detalhes sobre quando um componente é renderizado, no build ou por requisição, e de forma estática ou dinâmica.

## Como os dados entram na árvore \{#how-data-enters-the-tree}

Antes do RSC, apps Next.js normalmente coletavam dados do servidor com funções como `getStaticProps` ou `getServerSideProps` e depois os passavam à árvore de componentes como props. A busca de dados acontecia antes de a árvore ser renderizada. A árvore recebia os dados em vez de buscá-los durante a renderização.

```txt
Data
  ↓
Loader or API
  ↓
Props
  ↓
Component tree
```

Como um Server Component roda apenas no servidor, ele pode acessar recursos como um banco de dados, o sistema de arquivos, um serviço interno ou um segredo. O componente lê esses recursos durante a própria renderização, sem precisar de uma rota de API que primeiro exponha os dados ao cliente.

```tsx filename="app/page.tsx" switcher
import { PostList } from '@/app/ui/post-list'
import { getPosts } from '@/lib/data'

export default async function Page() {
  const posts = await getPosts() // runs on the server, during render
  return <PostList posts={posts} />
}
```

```jsx filename="app/page.js" switcher
import { PostList } from '@/app/ui/post-list'
import { getPosts } from '@/lib/data'

export default async function Page() {
  const posts = await getPosts() // runs on the server, during render
  return <PostList posts={posts} />
}
```

Com o RSC, um Server Component pode buscar dados enquanto renderiza. Uma etapa separada de carregamento de dados não precisa passar props iniciais para a árvore de componentes.

> **Bom saber:** como um Server Component pode ler segredos e dados exclusivos do servidor diretamente, seja deliberado sobre o que passa aos Client Components.
>
> As props são serializadas e enviadas ao navegador. Veja [Segurança de dados](/docs/app/guides/data-security#passing-data-from-server-to-client).

Server Components não precisam aguardar todos os dados antes de retornar a UI. Para fazer streaming de dados buscados no servidor para um Client Component, inicie a requisição em um Server Component e passe a promise pendente como prop.

O Client Component lê a promise como um recurso com [`use`](https://react.dev/reference/react/use#streaming-data-from-server-to-client). Enquanto a promise estiver pendente, a [fronteira do Suspense](/docs/app/glossary#suspense-boundary) mais próxima mostra o fallback dela. O Client Component é renderizado quando a promise resolve.

Como a requisição começa antes de o cliente rodar, o Client Component não precisa buscar os mesmos dados depois de montar. Você ainda pode precisar iniciar uma busca no navegador quando os dados solicitados dependerem de estado exclusivo do cliente ou de uma interação do usuário.

Requisições `fetch` idênticas são [memoizadas durante a renderização no servidor](/docs/app/api-reference/functions/fetch#memoization). Com [Cache Components](/docs/app/getting-started/caching), você pode armazenar em cache uma função de dados ou um componente e revalidar essa entrada de forma independente do restante da página. Para padrões de implementação, veja [Buscando dados](/docs/app/getting-started/fetching-data).

## Estado e interatividade \{#state-and-interactivity}

O código de um Server Component nunca chega ao navegador. O componente pode ser renderizado novamente quando o Next.js renderiza a rota, como em uma navegação, em um refresh ou após a revalidação.

O código de um Client Component chega ao navegador. O React hidrata o componente no carregamento inicial, e atualizações no cliente podem renderizá-lo novamente no navegador.

> **Bom saber:** no carregamento inicial, o RSC Payload é enviado junto com o HTML.
>
> Mutar diretamente os nós do DOM de um Server Component pode deixar o DOM fora de sincronia com a árvore de componentes do React.
>
> Para atualizar a saída de um Server Component, renderize o componente novamente no servidor. Quando o navegador recebe um novo RSC Payload, o React reconcilia a árvore de componentes e atualiza o DOM. Veja [Streaming](/docs/app/guides/streaming#the-component-payload).

`useState`, `useEffect` e os handlers de evento exigem código que roda no navegador e responde a atualizações. O código de um Server Component nunca chega ao navegador, então ele não pode usar essas APIs do lado do cliente.

O comportamento nativo do navegador e do HTML pode oferecer interatividade sem um Client Component. Por exemplo:

- Um elemento `<details>` abre e fecha.
- Um `<form>` pode ser enviado por meio de uma [Server Function](/docs/app/guides/server-actions) passada à prop `action`.
- Um elemento `<video controls>` toca e pausa.

Use um Client Component quando o comportamento exigir um estado do navegador que muda com o tempo, como um input controlado, um filtro ao vivo ou uma alça de arrastar. Um botão ou formulário não precisa de um Client Component quando o navegador fornece todo o comportamento necessário.

Para a lista prática do que pertence a cada ambiente, veja [Quando usar Server e Client Components](/docs/app/getting-started/server-and-client-components#when-to-use-server-and-client-components).

## Cruzando a fronteira \{#crossing-the-boundary}

Você marca um módulo como ponto de entrada do cliente adicionando a diretiva [`'use client'`](/docs/app/api-reference/directives/use-client) no topo do arquivo, antes de qualquer import. A diretiva desenha uma fronteira no grafo de módulos, e duas regras determinam o que cruza essa fronteira:

- **Código** cruza por meio de imports. Tudo o que um Client Component importa é incluído no [bundle do cliente](/docs/app/glossary#client-bundles).
- **Dados** cruzam por meio de props, e precisam ser [serializáveis](/docs/app/getting-started/server-and-client-components#passing-data-from-server-to-client-components), então funções como handlers de evento não podem cruzar.

> **Bom saber:**
>
> Passar uma função como prop de um Server Component para um Client Component gera um erro. Um handler de evento como `onClick` não pode cruzar a fronteira. Uma [Server Function](/docs/app/guides/server-actions) marcada com `'use server'` cruza como uma referência.
>
> Uma Server Function não se distingue de uma função comum pelo tipo dela. O plugin do TypeScript permite uma prop de Client Component tipada como função quando o nome dela é `action` ou termina em `Action`. O plugin sinaliza outras props de função.

Um elemento React já renderizado pode cruzar a fronteira, porque é um dado serializável. Passar a saída renderizada como `children` permite que um Server Component seja aninhado dentro de um Client Component, sem importar o código do Server Component para o grafo do cliente.

```tsx filename="app/page.tsx" switcher
import { Cart } from '@/app/ui/cart'
import { Modal } from '@/app/ui/modal'

// Page and Cart are Server Components. Modal is a Client Component
export default function Page() {
  return (
    <Modal title={<div>Your cart</div>}>
      <Cart />
    </Modal>
  )
}
```

```jsx filename="app/page.js" switcher
import { Cart } from '@/app/ui/cart'
import { Modal } from '@/app/ui/modal'

// Page and Cart are Server Components. Modal is a Client Component
export default function Page() {
  return (
    <Modal title={<div>Your cart</div>}>
      <Cart />
    </Modal>
  )
}
```

A prop `children` se comporta como qualquer outra prop. `Modal` recebe `title` e `children` como elementos React serializados e depois os renderiza nas posições definidas pela implementação dele.

```tsx filename="app/ui/modal.tsx" switcher
'use client'

import { useState, type ReactNode } from 'react'

export function Modal({
  title,
  children,
}: {
  title: ReactNode
  children: ReactNode
}) {
  const [open, setOpen] = useState(true)
  if (!open) return null

  return (
    <div role="dialog">
      <header>
        {title}
        <button onClick={() => setOpen(false)}>Close</button>
      </header>
      {children}
    </div>
  )
}
```

```jsx filename="app/ui/modal.js" switcher
'use client'

import { useState } from 'react'

export function Modal({ title, children }) {
  const [open, setOpen] = useState(true)
  if (!open) return null

  return (
    <div role="dialog">
      <header>
        {title}
        <button onClick={() => setOpen(false)}>Close</button>
      </header>
      {children}
    </div>
  )
}
```

Aqui, `Cart` roda no servidor, e `Modal` vê apenas a saída dele, nunca o código.

<details>
  <summary>Dono e pai</summary>

Neste exemplo, `Page` mostra dois papéis que o React mantém separados:

- O **dono** é o componente cujo código-fonte contém o JSX de um filho. `Page` é dono de `Modal` e de `Cart`.
- O **pai** contém diretamente o filho na árvore renderizada. `Modal` é o pai de `Cart`.

Como o dono de `Cart` é um Server Component, `Cart` é renderizado no servidor. `Modal` é apenas o pai, então ele recebe a saída de `Cart` para posicioná-la, mas não o código dela para executar. Essa separação permite que um Client Component exiba um Server Component que ele nunca importou.

</details>

<details>
  <summary>Componentes compostos através da fronteira</summary>

Componentes compostos podem expor subcomponentes como propriedades estáticas, como `Menu.Item` ou `Tabs.Panel`. Esse padrão funciona dentro de um mesmo grafo quando todas as peças são Server Components ou todas são Client Components.

O padrão quebra quando um membro estático cruza a fronteira. Um Server Component que importa um Client Component recebe uma referência de cliente em vez da função. Como resultado, `Menu.Item` é `undefined`, e o React gera o erro "Element type is invalid."

Use um Client Component composto a partir de outro Client Component. Para usar as peças dele em um Server Component, exponha-as como exports nomeados em vez de propriedades estáticas.

</details>

Você só precisa de `'use client'` na entrada de uma subárvore do cliente, não em cada arquivo dentro dela. Todo módulo importado a partir dessa entrada passa a fazer parte do grafo de módulos do cliente.

Para deixar um componente compartilhado sem alterações, crie um wrapper de Client Component que o importa e coloque a diretiva no wrapper. O wrapper mantém o módulo compartilhado intacto e posiciona a fronteira mais perto do código do seu app. Isso também evita adicionar a diretiva a todo componente compartilhado que chama `useState` ou `useEffect`.

Se código do cliente entrar no grafo do servidor sem uma fronteira, o compilador indica onde você precisa da diretiva.

Para mais padrões, veja [Intercalando Server e Client Components](/docs/app/getting-started/server-and-client-components#interleaving-server-and-client-components).

Para as outras diretivas usadas no Next.js, veja a documentação de [diretivas](/docs/app/api-reference/directives).
