A [Regeneração Estática Incremental (ISR)](/docs/app/glossary#incremental-static-regeneration-isr) com [`cacheComponents`](/docs/app/api-reference/config/next-config-js/cacheComponents) e [Partial Prefetching](/docs/app/api-reference/config/next-config-js/partialPrefetching) oferece a todas as rotas uma primeira visita instantânea, mesmo para URLs que não foram incluídas no build.

Durante o build, o Partial Prerendering divide cada renderização em duas partes:

- A **App Shell**: a parte genérica e reutilizável da página, que não depende de dados da URL
- O restante do conteúdo renderizável estaticamente: as pré-renderizações específicas de parâmetros para as URLs que você lista em [`generateStaticParams`](/docs/app/api-reference/functions/generate-static-params)

Para uma visita a uma URL cujos parâmetros foram incluídos em `generateStaticParams`, o Next.js serve a página totalmente prerenderizada a partir do cache. Para uma visita a uma URL cujos parâmetros não foram incluídos, o Next.js serve a App Shell instantaneamente e, em seguida, a atualiza em segundo plano com os parâmetros já conhecidos. As visitas seguintes a essa URL recebem o resultado atualizado do cache, pulando a App Shell por completo.

Se você usou [ISR](/docs/app/guides/incremental-static-regeneration) ou [`fallback: true`](https://nextjs.org/docs/pages/api-reference/functions/get-static-paths#fallback-true) no Pages Router, esta é a equivalente em Cache Components.

Ative o [`cacheComponents`](/docs/app/api-reference/config/next-config-js/cacheComponents) e o [Partial Prefetching](/docs/app/api-reference/config/next-config-js/partialPrefetching).

Cache Components prerenderiza uma shell estática que pode incluir UI de fallback. Para caminhos que não são retornados por `generateStaticParams`, o Next.js pode renderizar o caminho sob demanda e armazenar o resultado completo no cache ISR.

O Partial Prefetching determina se o fallback é servido antes de a renderização específica da URL terminar:

- **Com Partial Prefetching:** você pode usar `await` em `params` dentro de `<Suspense>`. O Next.js pode servir imediatamente o fallback para um caminho não listado, renderizar o conteúdo específico da URL e armazenar o resultado completo no cache ISR.
- **Sem Partial Prefetching:** a primeira requisição para um caminho não listado precisa esperar a renderização específica da URL terminar. Faça o `await` em `params` fora de qualquer fronteira de `<Suspense>`, incluindo uma criada pelo [`loading.tsx`](/docs/app/api-reference/file-conventions/loading), para que o Next.js crie uma entrada ISR para essa URL.

> **Bom saber:** sem Partial Prefetching, usar `await` em `params` dentro de `<Suspense>` faz o Next.js continuar servindo o fallback compartilhado, em vez de criar uma entrada ISR específica da URL. Os dados buscados pela rota ainda podem ser armazenados em cache de forma independente.

```ts filename="next.config.ts" highlight={4-5}
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

export default nextConfig
```

## Exemplo \{#example}

Vamos montar um catálogo de produtos com layouts de categoria e páginas de detalhe de produto usando a [Recipe API](https://next-recipe-api.vercel.dev/). Você encontra os recursos usados neste exemplo aqui:

- [Demonstração](https://partial-fallbacks.labs.vercel.dev/)
- [Código](https://github.com/nextjs/partial-fallbacks)

### Prepare as suas rotas \{#prepare-your-routes}

Use [`generateStaticParams`](/docs/app/api-reference/functions/generate-static-params) para definir quais valores de parâmetro devem ser prerenderizados. Ao renderizar essas rotas, os valores dos parâmetros são conhecidos em tempo de build. O processo de prerendering monta uma shell estática até encontrar uma [API de tempo de requisição](/docs/app/glossary#request-time-apis) ou dados sem cache. Veja [Prerendering](/docs/app/getting-started/caching#prerendering) para mais detalhes.

O layout de categoria prerenderiza duas categorias:

```tsx filename="app/[category]/layout.tsx" highlight={5-8}
import Link from 'next/link'
import { Suspense } from 'react'
import { getCategory, getTopCategories } from '../lib/data'

export async function generateStaticParams() {
  const categories = await getTopCategories()
  return categories.map((c) => ({ category: c.slug }))
}

async function CategoryHeader({
  params,
}: Pick<LayoutProps<'/[category]'>, 'params'>) {
  const { category } = await params
  const data = await getCategory(category)

  return (
    <div>
      <Link href="/">&larr; All categories</Link>
      <h1>{data?.name ?? 'Category'}</h1>
      {data?.description && <p>{data.description}</p>}
    </div>
  )
}

export default function CategoryLayout(props: LayoutProps<'/[category]'>) {
  return (
    <div>
      <Suspense fallback={<div>Loading...</div>}>
        <CategoryHeader params={props.params} />
      </Suspense>
      {props.children}
    </div>
  )
}
```

Observe que `CategoryLayout` não faz `await props.params` por conta própria. Em vez disso, ele passa a promise `params` para `CategoryHeader` dentro de `<Suspense>`. O `await` acontece dentro da fronteira; assim, para categorias desconhecidas, o Next.js ainda consegue gerar a App Shell. Mantenha a leitura dentro da fronteira, mesmo para as categorias cobertas por `generateStaticParams`. Um parâmetro conhecido estaticamente ainda pertence a uma única URL, então fazer `await` dele acima da fronteira do Suspense amarraria a App Shell deste layout a essa URL. Veja [Navegação instantânea](/docs/app/guides/instant-navigation) para estruturar as rotas dessa forma.

A página de produto prerenderiza um produto por categoria. `generateStaticParams` recebe o parâmetro `category` do pai:

```tsx filename="app/[category]/[product]/page.tsx" highlight={5-12}
import { Suspense } from 'react'
import Link from 'next/link'
import { getProduct, getPopularProducts } from '../../lib/data'

export async function generateStaticParams({
  params,
}: {
  params: { category: string }
}) {
  const products = await getPopularProducts(params.category)
  return products.map((p) => ({ product: p.slug }))
}

async function ProductDetails(props: PageProps<'/[category]/[product]'>) {
  const { category, product } = await props.params
  const data = await getProduct(category, product)

  if (!data) {
    return <p>Product not found.</p>
  }

  return (
    <>
      <Link href={`/${category}`} prefetch={true}>
        &larr; Back to products
      </Link>
      <h2>{data.name}</h2>
      <p>${data.price}</p>
      <p>{data.description}</p>
    </>
  )
}

export default function ProductPage(props: PageProps<'/[category]/[product]'>) {
  return (
    <div>
      <Suspense fallback={<div>Loading product...</div>}>
        <ProductDetails {...props} />
      </Suspense>
    </div>
  )
}
```

> **Bom saber:** você também pode usar arquivos [`loading.tsx`](/docs/app/api-reference/file-conventions/loading) em vez de `<Suspense>` no JSX. O `loading.tsx` coloca a fronteira na borda do segmento, enquanto o `<Suspense>` inline permite posicioná-la em qualquer lugar da árvore.

Os auxiliares de dados usam `'use cache'` no nível do módulo, para que todas as funções exportadas sejam armazenadas em cache. Assim, os resultados delas podem ser incluídos na shell estática:

```ts filename="app/lib/data.ts" highlight={1}
'use cache'

const API = 'https://next-recipe-api.vercel.dev'

export async function getCategory(slug: string) {
  const res = await fetch(`${API}/categories/${slug}`)
  if (!res.ok) return null
  return res.json()
}

export async function getProduct(category: string, slug: string) {
  const res = await fetch(`${API}/products/${category}/${slug}`)
  if (!res.ok) return null
  return res.json()
}

export async function getTopCategories() {
  const res = await fetch(`${API}/categories`)
  const categories = await res.json()
  return categories.slice(0, 2)
}

export async function getPopularProducts(category: string) {
  const res = await fetch(`${API}/products?category=${category}`)
  const products = await res.json()
  return products.slice(0, 1)
}
```

Se um componente acessa uma API de tempo de requisição, como `cookies()` ou `headers()`, envolva-o em `<Suspense>`. Durante o prerendering, o Next.js inclui o fallback mais próximo na shell estática. Para manter o componente fora de um `<Link prefetch={true}>` também, faça `await` em [`navigation()`](/docs/app/api-reference/functions/navigation) antes do acesso em tempo de requisição. Veja [Mantenha o prefetch estático](/docs/app/guides/optimizing-prefetching#keep-the-prefetch-static).

### No build \{#at-build-time}

Quando você executa `next build`, o Next.js prerenderiza o layout para cada categoria conhecida (`tops`, `shorts`), mais uma renderização em que `await params` fica suspenso, produzindo a App Shell de `[category]`.

Ele também prerenderiza a página de cada produto conhecido em cada categoria (`tee` em `tops`, `joggers` em `shorts`), mais uma renderização em que `await params` fica suspenso, produzindo a App Shell de `[product]`.

Essas combinações resultam em:

- `/tops/tee`, `/shorts/joggers`: páginas totalmente estáticas, com os dois parâmetros conhecidos
- `/tops/[product]`, `/shorts/[product]`: cabeçalho da categoria renderizado, e o produto mostra o fallback
- `/[category]/[product]`: ambos mostram o fallback

Os parâmetros desconhecidos de uma shell sempre vêm por último, na ordem da rota. Uma URL não pode ter um segmento desconhecido no meio, então não existe a shell `/[category]/tee`. Uma visita com uma categoria não listada recebe `/[category]/[product]`, qualquer que seja o produto.

### Em tempo de execução \{#at-runtime}

Um visitante navega até `/tops/tee`. Os dois parâmetros foram prerenderizados. Ele recebe uma página totalmente estática.

A primeira visita a `/tops/overshirt`: o produto `overshirt` é desconhecido, mas a categoria `tops` foi prerenderizada. O Next.js serve a App Shell de `/tops/[product]` com o cabeçalho da categoria já renderizado. O produto chega em streaming.

A primeira visita a `/shoes/basketball-shoes`: nenhum dos parâmetros foi prerenderizado. O Next.js serve a App Shell genérica de `/[category]/[product]`. Tanto a categoria quanto o produto chegam em streaming.

Após a primeira visita, o Next.js renderiza essas rotas em segundo plano com os parâmetros já conhecidos. O próximo visitante das mesmas URLs recebe o resultado atualizado.

Quando um [`<Link prefetch={true}>`](/docs/app/api-reference/components/link#prefetch) para uma URL não listada entra na viewport, o Next.js inicia a atualização em segundo plano antes do clique, assim como faria em uma primeira visita, para que a navegação caia no resultado atualizado.

Os links para essas páginas precisam de `prefetch={true}`. Um `<Link>` padrão faz prefetch apenas da App Shell, que é compartilhada pelos links da mesma rota.

> **Bom saber:** a App Shell para parâmetros não listados é servida a partir do Next.js 16.3. Versões anteriores aguardam uma renderização completa no servidor antes de enviar a resposta.

### Aguarde a saída estática completa \{#wait-for-complete-static-output}

Para um parâmetro não listado, o [`ensureStatic = 'navigation'`](/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic#navigation) faz a primeira requisição aguardar a página estática completa. Sem esse requisito, o Next.js pode devolver um fallback prerenderizado enquanto gera a página em segundo plano. O Next.js armazena a página completa para as requisições seguintes.

### O que a atualização produz \{#what-the-upgrade-produces}

Após a primeira visita, o Next.js renderiza a página em segundo plano com os parâmetros conhecidos e tenta empurrar a fronteira estática o mais para baixo possível na árvore de componentes:

- Se todo acesso a dados estiver em cache e todos os parâmetros forem resolvidos, a atualização produz uma **página totalmente estática**.
- Se todos os parâmetros forem resolvidos, mas a renderização ainda alcançar dados sem cache ou APIs de tempo de requisição (`cookies()`, `headers()`) envolvidas em fronteiras de `<Suspense>`, a atualização produz uma **página em cache com esses fallbacks**. As partes sem cache ou específicas da requisição chegam em streaming no momento da requisição.

## Escolhendo o que prerenderizar \{#choosing-what-to-prerender}

Nem toda rota precisa ser prerenderizada. Cada página prerenderizada aumenta o trabalho do build e gera uma saída que precisa ser armazenada e publicada. Muitas rotas podem nunca ser visitadas antes do próximo deploy, tornando esse trabalho desnecessário.

Em vez disso, use [`generateStaticParams`](/docs/app/api-reference/functions/generate-static-params) para prerenderizar as rotas que mais se beneficiam de estar prontas antecipadamente, como páginas populares ou conteúdo previsível. Rotas menos visitadas são geradas sob demanda e atualizadas após a primeira visita, então você não gasta tempo de build e armazenamento com páginas que talvez nunca sejam requisitadas.

## Vindo do Pages Router \{#coming-from-the-pages-router}

Se você está migrando do Pages Router:

- `fallback: true` em `getStaticPaths` corresponde a Cache Components com Partial Prefetching. Os visitantes recebem um fallback de `<Suspense>` instantaneamente, e o Next.js armazena a rota completa para as visitas seguintes.

- `getStaticProps` com `revalidate` corresponde a `'use cache'` com [`cacheLife`](/docs/app/api-reference/functions/cacheLife).
- `getStaticPaths` corresponde a [`generateStaticParams`](/docs/app/api-reference/functions/generate-static-params).
