O Next.js foi projetado para oferecer uma ótima experiência de desenvolvimento. Conforme seu app cresce, você pode notar tempos de compilação mais longos durante o desenvolvimento local. Este guia vai ajudar a identificar e corrigir problemas comuns de performance na compilação.

## Desenvolvimento local vs. produção \{#local-dev-vs-production}

O processo de desenvolvimento com `next dev` é diferente de `next build` e `next start`.

`next dev` compila as rotas do seu app conforme você as abre ou navega até elas. Isso permite iniciar o dev server sem esperar que todas as rotas do app sejam compiladas, o que é mais rápido e usa menos memória. Já um build de produção aplica outras otimizações, como minificar arquivos e gerar hashes de conteúdo, que não são necessárias no desenvolvimento local.

## Configuração do sistema \{#system-configuration}

### 1. Verifique o antivírus do seu computador \{#1-check-your-computers-antivirus}

Softwares antivírus podem deixar o acesso aos arquivos mais lento. Isso é mais comum em máquinas Windows, mas pode ser um problema em qualquer sistema com uma ferramenta antivírus instalada.

**No Windows,** você pode adicionar seu projeto à [lista de exclusões do Microsoft Defender Antivirus](https://support.microsoft.com/en-us/windows/virus-and-threat-protection-in-the-windows-security-app-1362f4cd-d71a-b52a-0b66-c2820032b65e#bkmk_threat-protection-settings).

1. Abra o aplicativo **"Segurança do Windows"** e selecione **"Proteção contra vírus e ameaças"** &rarr; **"Gerenciar configurações"** &rarr; **"Adicionar ou remover exclusões"**.
2. Adicione uma exclusão de **"Pasta"**. Selecione a pasta do seu projeto.

Como alternativa, você pode ativar e usar um [Dev Drive](#3-windows-use-dev-drive-or-wsl-2), que [usa o "modo de performance" do Microsoft Defender](https://learn.microsoft.com/en-us/windows/dev-drive/#understanding-security-risks-and-trust-in-relation-to-dev-drive).

**No macOS,** você pode desativar o [Gatekeeper](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web) no seu terminal.

1. Execute `sudo spctl developer-mode enable-terminal` no seu terminal.
2. Abra o app **"Ajustes do Sistema"** e selecione **"Privacidade e Segurança"** &rarr; **"Ferramentas para Desenvolvedores"**.
3. Confirme que seu terminal está listado e ativado. Se você usa um terminal de terceiros, como iTerm ou Ghostty, adicione-o à lista.
4. Reinicie seu terminal.

### 2. Evite armadilhas comuns do Docker \{#2-avoid-common-docker-pitfalls}

Se você usa Docker para desenvolvimento no Mac ou no Windows, pode notar uma performance bem mais lenta do que rodando o Next.js sem Docker.

Isso geralmente não é um problema em produção, nem quando o Docker roda nativamente no Linux, porque os arquivos do projeto não atravessam a camada de compartilhamento de arquivos entre o host e a VM do Docker Desktop.

Quando os arquivos do projeto ficam no host macOS ou Windows e são montados em um container pelo Docker Desktop ou ferramentas semelhantes, a camada de compartilhamento de arquivos entre o host e a VM pode atrasar ou impedir a propagação dos eventos do sistema de arquivos. Isso pode fazer o [Fast Refresh](/docs/architecture/fast-refresh) levar segundos ou até minutos, enquanto a mesma aplicação mostra as atualizações rapidamente quando desenvolvida diretamente no host, sem Docker.

Para a melhor experiência de desenvolvimento:

- Rode o Next.js sem Docker (`npm run dev` ou `pnpm dev`) durante o desenvolvimento.
- Reserve o Docker para deploys de produção e para testar builds de produção.
- Se você precisar usar Docker para desenvolvimento, considere rodar o Docker nativamente em uma máquina Linux ou em uma máquina virtual configurada manualmente. Se usar uma máquina virtual configurada manualmente, mova o código-fonte para dentro da VM e não o compartilhe a partir do host.
- Se você usa o Docker Desktop, avalie o uso de [compartilhamentos de arquivos sincronizados](https://docs.docker.com/desktop/features/synchronized-file-sharing/). Eles ainda adicionam latência em comparação com rodar o Next.js diretamente no host, mas podem melhorar a confiabilidade do monitoramento de arquivos sem recorrer a polling.
- Evite usar `watchOptions.pollIntervalMs` no `next.config.js` para contornar problemas do Fast Refresh. Use isso apenas como último recurso. O polling adiciona latência significativa e pode aumentar muito o uso de CPU e de I/O.

[Saiba mais sobre deploy com Docker](/docs/app/getting-started/deploying#docker) para uso em produção.

### 3. (Windows) Use Dev Drive ou WSL 2 \{#3-windows-use-dev-drive-or-wsl-2}

O recurso Dev Drive do Windows 11 usa um sistema de arquivos alternativo para melhorar a performance em fluxos de trabalho de desenvolvimento comuns. A [Microsoft tem um guia explicando como configurá-lo](https://learn.microsoft.com/en-us/windows/dev-drive/).

Como alternativa, o Windows oferece uma forma simples de configurar uma máquina virtual Linux usando o [Windows Subsystem for Linux](https://learn.microsoft.com/en-us/windows/wsl/). Você pode ter uma performance melhor usando o WSL 2.

Ao usar o WSL 2, armazene o diretório do projeto dentro do sistema de arquivos da máquina virtual (por exemplo, `/home/$USER/project`) e não em um drive do Windows (por exemplo, `C:\` ou `/mnt/c`). Se você não fizer isso, a performance será pior e as atualizações de arquivos podem não ser refletidas corretamente no desenvolvimento.

## Melhorando a performance do desenvolvimento do app \{#improving-application-development-performance}

### 1. Atualize o Next.js e use o Turbopack \{#1-update-nextjs-and-use-turbopack}

Garanta que você está usando a versão mais recente do Next.js. Cada nova versão costuma trazer melhorias de performance.

O Turbopack agora é o bundler padrão para o desenvolvimento com Next.js e oferece melhorias significativas de performance em relação ao webpack.

```bash package="pnpm"
pnpm add next@latest
pnpm dev  # Turbopack is used by default
```

```bash package="npm"
npm install next@latest
npm run dev  # Turbopack is used by default
```

```bash package="yarn"
yarn add next@latest
yarn dev  # Turbopack is used by default
```

```bash package="bun"
bun add next@latest
bun dev  # Turbopack is used by default
```

Se você precisar usar o Webpack em vez do Turbopack, pode optar por ele:

```bash package="pnpm"
pnpm dev --webpack
```

```bash package="npm"
npm run dev -- --webpack
```

```bash package="yarn"
yarn dev --webpack
```

```bash package="bun"
bun run dev --webpack
```

[Saiba mais sobre o Turbopack](/blog/turbopack-for-development-stable). Veja nossos [guias de atualização](/docs/app/guides/upgrading) e codemods para mais informações.

### 2. Verifique seus imports \{#2-check-your-imports}

A forma como você importa o código pode afetar bastante o tempo de compilação e de bundling. Saiba mais sobre [otimização do bundling de pacotes](/docs/app/guides/package-bundling) e conheça ferramentas como [Dependency Cruiser](https://github.com/sverweij/dependency-cruiser) ou [Madge](https://github.com/pahen/madge).

#### Bibliotecas de ícones \{#icon-libraries}

Bibliotecas como `@material-ui/icons`, `@phosphor-icons/react` ou `react-icons` podem importar milhares de ícones, mesmo que você use apenas alguns. Tente importar somente os ícones de que precisa:

```jsx
// Instead of this:
import { TriangleIcon } from '@phosphor-icons/react'

// Do this:
import { TriangleIcon } from '@phosphor-icons/react/dist/csr/Triangle'
```

Muitas vezes você encontra o padrão de import a usar na documentação da biblioteca de ícones que está usando. Este exemplo segue a recomendação do [`@phosphor-icons/react`](https://www.npmjs.com/package/@phosphor-icons/react#import-performance-optimization).

Bibliotecas como o `react-icons` incluem vários conjuntos de ícones diferentes. Escolha um conjunto e mantenha-se nele.

Por exemplo, se seu app usa o `react-icons` e importa todos estes:

- `pi` (Phosphor Icons)
- `md` (Material Design Icons)
- `tb` (tabler-icons)
- `cg` (cssgg)

Juntos, eles somam dezenas de milhares de módulos que o compilador precisa processar, mesmo que você use apenas um import de cada um.

#### Barrel files \{#barrel-files}

"Barrel files" são arquivos que exportam muitos itens de outros arquivos. Eles podem deixar os builds mais lentos, porque o compilador precisa analisar esses arquivos para descobrir se há efeitos colaterais no escopo do módulo ao usar o import.

Sempre que possível, importe diretamente dos arquivos específicos. [Saiba mais sobre barrel files](https://vercel.com/blog/how-we-optimized-package-imports-in-next-js) e sobre as otimizações nativas do Next.js.

#### Otimize os imports de pacotes \{#optimize-package-imports}

O Next.js pode otimizar automaticamente os imports de determinados pacotes. Se você usa pacotes que dependem de barrel files, adicione-os ao seu `next.config.js`:

```jsx
module.exports = {
  experimental: {
    optimizePackageImports: ['package-name'],
  },
}
```

O Turbopack analisa e otimiza os imports automaticamente. Ele não exige essa configuração.

### 3. Verifique sua configuração do Tailwind CSS \{#3-check-your-tailwind-css-setup}

Se você usa Tailwind CSS, confira se ele está configurado corretamente.

Um erro comum é configurar o array `content` de um jeito que inclui `node_modules` ou outras pastas grandes com arquivos que não deveriam ser lidos.

O Tailwind CSS na versão 3.4.8 ou mais recente avisa sobre configurações que podem deixar o build mais lento.

1. No seu `tailwind.config.js`, seja específico sobre quais arquivos ler:

   ```jsx
   module.exports = {
     content: [
       './src/**/*.{js,ts,jsx,tsx}', // Good
       // This might be too broad
       // It will match `packages/**/node_modules` too
       // '../../packages/**/*.{js,ts,jsx,tsx}',
     ],
   }
   ```

2. Evite ler arquivos desnecessários:

   ```jsx
   module.exports = {
     content: [
       // Better - only scans the 'src' folder
       '../../packages/ui/src/**/*.{js,ts,jsx,tsx}',
     ],
   }
   ```

### 4. Verifique as configurações personalizadas do webpack \{#4-check-custom-webpack-settings}

Se você adicionou configurações personalizadas do webpack, elas podem estar deixando a compilação mais lenta.

Avalie se você realmente precisa delas no desenvolvimento local. Você pode, opcionalmente, incluir certas ferramentas apenas nos builds de produção, ou explorar o uso do bundler padrão, o Turbopack, configurando [loaders](/docs/app/api-reference/config/next-config-js/turbopack#configuring-webpack-loaders) em vez disso.

### 5. Otimize o uso de memória \{#5-optimize-memory-usage}

Se seu app for muito grande, ele pode precisar de mais memória.

[Saiba mais sobre como otimizar o uso de memória](/docs/app/guides/memory-usage).

### 6. Server Components e busca de dados \{#6-server-components-and-data-fetching}

Mudanças em Server Components fazem a página inteira renderizar novamente localmente para mostrar as novas alterações, o que inclui buscar novos dados para o componente.

A opção experimental `serverComponentsHmrCache` permite armazenar em cache as respostas de `fetch` em Server Components entre os refreshes do Hot Module Replacement (HMR) no desenvolvimento local. Isso resulta em respostas mais rápidas e em menos custos com chamadas de API cobradas.

[Saiba mais sobre a opção experimental](/docs/app/api-reference/config/next-config-js/serverComponentsHmrCache).

## Ferramentas para encontrar problemas \{#tools-for-finding-problems}

### Log detalhado de fetch \{#detailed-fetch-logging}

Use a opção `logging.fetches` no seu arquivo `next.config.js` para ver informações mais detalhadas sobre o que está acontecendo durante o desenvolvimento:

```js
module.exports = {
  logging: {
    fetches: {
      fullUrl: true,
    },
  },
}
```

[Saiba mais sobre o log de fetch](/docs/app/api-reference/config/next-config-js/logging).

### Rastreamento do Turbopack \{#turbopack-tracing}

O rastreamento do Turbopack é uma ferramenta que ajuda a entender a performance do seu app durante o desenvolvimento local.
Ele fornece informações detalhadas sobre o tempo que cada módulo leva para compilar e como os módulos se relacionam.

1. Garanta que você tem a versão mais recente do Next.js instalada.
1. Gere um arquivo de rastreamento do Turbopack:

   ```bash package="pnpm"
   pnpm dev --internal-trace
   ```

   ```bash package="npm"
   npm run dev -- --internal-trace
   ```

   ```bash package="yarn"
   yarn dev --internal-trace
   ```

   ```bash package="bun"
   bun dev --internal-trace
   ```

1. Navegue pelo seu app ou faça edições nos arquivos para reproduzir o problema.
1. Pare o dev server do Next.js.
1. Um arquivo chamado `trace-turbopack.bin` ficará disponível na pasta `.next-profiles`.
1. Você pode interpretar o arquivo usando `npx next internal trace [path-to-file]`:

   ```bash
   npx next internal trace .next-profiles/trace-turbopack.bin
   ```

   Em versões em que `trace` não está disponível, o comando se chamava `turbo-trace-server`:

   ```bash
   npx next internal turbo-trace-server .next-profiles/trace-turbopack.bin
   ```

1. Depois que o trace server estiver rodando, você pode visualizar o rastreamento em https://trace.nextjs.org/.
1. Por padrão, o visualizador agrega os tempos. Para ver cada tempo individualmente, troque de "Aggregated in order" para "Spans in order" no canto superior direito do visualizador.

> **Bom saber**: o arquivo de rastreamento fica na pasta `.next-profiles`, na raiz do projeto.
