Antes de colocar seu app Next.js em produção, há algumas otimizações e padrões que você deve considerar implementar para a melhor experiência do usuário, performance e segurança.

Esta página reúne boas práticas que você pode usar como referência ao [construir seu app](#during-development) e [antes de ir para produção](#before-going-to-production), além das [otimizações automáticas do Next.js](#automatic-optimizations) que você deve conhecer.

## Otimizações automáticas \{#automatic-optimizations}

Estas otimizações do Next.js vêm habilitadas por padrão e não exigem configuração:

<AppOnly>

- **[Server Components](/docs/app/getting-started/server-and-client-components):** O Next.js usa Server Components por padrão. Server Components rodam no servidor e não precisam de JavaScript para renderizar no cliente. Por isso, não impactam o tamanho dos seus bundles de JavaScript no cliente. Depois, você pode usar [Client Components](/docs/app/getting-started/server-and-client-components) quando precisar de interatividade.
- **[Code-splitting](/docs/app/getting-started/linking-and-navigating#how-navigation-works):** Server Components habilitam o code-splitting automático por segmentos de rota. Você também pode considerar [lazy loading](/docs/app/guides/lazy-loading) em Client Components e bibliotecas de terceiros, quando fizer sentido.
- **[Prefetching](/docs/app/getting-started/linking-and-navigating#prefetching):** Quando um link para uma nova rota entra na viewport do usuário, o Next.js faz o prefetch da rota em segundo plano. Isso torna a navegação para novas rotas quase instantânea. Você pode desativar o prefetching, quando fizer sentido.
- **[Prerendering](/docs/app/glossary#prerendering):** O Next.js faz o prerendering de Server e Client Components no servidor, em tempo de build, e armazena em cache o resultado renderizado para melhorar a performance do seu app. Você pode optar pelo [Dynamic Rendering](/docs/app/glossary#dynamic-rendering) para rotas específicas, quando fizer sentido. {/* TODO: Update when PPR is stable */}
- **[Caching](/docs/app/getting-started/caching):** O Next.js faz cache de requisições de dados, do resultado renderizado de Server e Client Components, de assets estáticos e de outros recursos, para reduzir o número de requisições de rede ao seu servidor, banco de dados e serviços de backend. Você pode desativar o cache, quando fizer sentido.

</AppOnly>

<PagesOnly>

- **[Code-splitting](/docs/pages/building-your-application/routing/pages-and-layouts):** O Next.js faz o code-splitting do código do seu app automaticamente, por páginas. Isso significa que, na navegação, só o código necessário para a página atual é carregado. Você também pode considerar [lazy loading](/docs/pages/guides/lazy-loading) para bibliotecas de terceiros, quando fizer sentido.
- **[Prefetching](/docs/pages/api-reference/components/link#prefetch):** Quando um link para uma nova rota entra na viewport do usuário, o Next.js faz o prefetch da rota em segundo plano. Isso torna a navegação para novas rotas quase instantânea. Você pode desativar o prefetching, quando fizer sentido.
- **[Automatic Static Optimization](/docs/pages/building-your-application/rendering/automatic-static-optimization):** O Next.js determina automaticamente que uma página é estática (pode passar por prerendering) se ela não tiver requisitos de dados bloqueantes. Páginas otimizadas podem ser armazenadas em cache e servidas ao usuário final a partir de vários locais de CDN. Você pode optar pelo [Server-side Rendering](/docs/pages/building-your-application/data-fetching/get-server-side-props), quando fizer sentido.

</PagesOnly>

Esses padrões têm como objetivo melhorar a performance do seu app e reduzir o custo e a quantidade de dados transferidos em cada requisição de rede.

## Durante o desenvolvimento \{#during-development}

Enquanto constrói seu app, recomendamos usar os recursos a seguir para garantir a melhor performance e experiência do usuário:

### Roteamento e renderização \{#routing-and-rendering}

<AppOnly>

- **[Layouts](/docs/app/api-reference/file-conventions/layout):** Use layouts para compartilhar a UI entre páginas e habilitar a [renderização parcial](/docs/app/getting-started/linking-and-navigating#client-side-transitions) na navegação.
- **[Componente `<Link>`](/docs/app/api-reference/components/link):** Use o componente `<Link>` para [navegação no cliente e prefetching](/docs/app/getting-started/linking-and-navigating#how-navigation-works).
- **[Tratamento de erros](/docs/app/getting-started/error-handling):** Trate com elegância [erros genéricos](/docs/app/getting-started/error-handling) e [erros 404](/docs/app/api-reference/file-conventions/not-found) em produção, criando páginas de erro personalizadas.
- **[Client e Server Components](/docs/app/getting-started/server-and-client-components#examples):** Siga os padrões de composição recomendados para Server e Client Components, e verifique a posição das suas [fronteiras `"use client"`](/docs/app/getting-started/server-and-client-components#reducing-js-bundle-size) para não aumentar desnecessariamente o bundle de JavaScript no cliente.
- **[APIs de tempo de requisição](/docs/app/getting-started/caching#working-with-runtime-apis):** APIs de tempo de requisição, como [`cookies`](/docs/app/api-reference/functions/cookies) e a prop [`searchParams`](/docs/app/api-reference/file-conventions/page#searchparams-optional), leem dados que só são conhecidos quando o usuário faz uma requisição. Envolva os componentes que as usam em `<Suspense>` para que o restante da rota ainda possa ser prerenderizado. Sem Cache Components, usá-las faz a rota inteira entrar no [Dynamic Rendering](/docs/app/glossary#dynamic-rendering) (ou todo o seu app, se usadas no [Root Layout](/docs/app/api-reference/file-conventions/layout#root-layout)).

</AppOnly>

<PagesOnly>

- **[Componente `<Link>`](/docs/pages/building-your-application/routing/linking-and-navigating):** Use o componente `<Link>` para navegação no cliente e prefetching.
- **[Erros personalizados](/docs/pages/building-your-application/routing/custom-error):** Trate com elegância os [erros 500](/docs/pages/building-your-application/routing/custom-error#500-page) e [404](/docs/pages/building-your-application/routing/custom-error#404-page)

</PagesOnly>

### Busca de dados e caching \{#data-fetching-and-caching}

<AppOnly>

- **[Server Components](/docs/app/getting-started/fetching-data):** Aproveite os benefícios de buscar dados no servidor usando Server Components.
- **[Route Handlers](/docs/app/api-reference/file-conventions/route):** Use Route Handlers para acessar seus recursos de backend a partir de Client Components. Mas não chame Route Handlers a partir de Server Components, para evitar uma requisição extra ao servidor.
- **[Streaming](/docs/app/api-reference/file-conventions/loading):** Use Loading UI e React Suspense para enviar a UI progressivamente do servidor para o cliente, e evitar que a rota inteira fique bloqueada enquanto os dados são buscados.
- **[Busca de dados em paralelo](/docs/app/getting-started/fetching-data#parallel-data-fetching):** Reduza as cascatas de requisições buscando dados em paralelo, quando fizer sentido.
- **[Data Caching](/docs/app/getting-started/caching):** Verifique se suas requisições de dados estão sendo armazenadas em cache e opte pelo caching, quando fizer sentido. Garanta que requisições que não usam `fetch` sejam [armazenadas em cache](/docs/app/api-reference/functions/unstable_cache).
- **[Imagens estáticas](/docs/app/api-reference/file-conventions/public-folder):** Use o diretório `public` para armazenar automaticamente em cache os assets estáticos do seu app, por exemplo, imagens.

</AppOnly>

<PagesOnly>

- **[API Routes](/docs/pages/building-your-application/routing/api-routes):** Use Route Handlers para acessar seus recursos de backend e impedir que segredos sensíveis sejam expostos ao cliente.
- **[Data Caching](/docs/pages/building-your-application/data-fetching/get-static-props):** Verifique se suas requisições de dados estão sendo armazenadas em cache e opte pelo caching, quando fizer sentido. Garanta que as requisições que não usam `getStaticProps` sejam armazenadas em cache, quando fizer sentido.
- **[Incremental Static Regeneration](/docs/pages/guides/incremental-static-regeneration):** Use Incremental Static Regeneration para atualizar páginas estáticas depois que elas foram geradas, sem fazer o build de todo o seu site novamente.
- **[Imagens estáticas](/docs/pages/api-reference/file-conventions/public-folder):** Use o diretório `public` para armazenar automaticamente em cache os assets estáticos do seu app, por exemplo, imagens.

</PagesOnly>

### UI e acessibilidade \{#ui-and-accessibility}

<AppOnly>

- **[Formulários e validação](/docs/app/guides/forms):** Use Server Actions para lidar com envios de formulário, validação no servidor e tratamento de erros.
- **[UI de erro global](/docs/app/api-reference/file-conventions/error#global-error):** Adicione `app/global-error.tsx` para oferecer uma UI de fallback consistente e acessível, com recuperação para erros não tratados em todo o seu app.
- **[404 global](/docs/app/api-reference/file-conventions/not-found#global-not-foundjs-experimental):** Adicione `app/global-not-found.tsx` para servir um 404 acessível para rotas não encontradas em todo o seu app.

</AppOnly>

- **[Módulo de fontes](/docs/app/api-reference/components/font):** Otimize as fontes usando o Módulo de fontes, que hospeda automaticamente os arquivos de fonte junto com os demais assets estáticos, remove requisições de rede externas e reduz o [layout shift](https://web.dev/articles/cls).
- **[Componente `<Image>`](/docs/app/api-reference/components/image):** Otimize imagens usando o componente Image, que as otimiza automaticamente, evita o layout shift e as serve em formatos modernos, como WebP.
- **[Componente `<Script>`](/docs/app/guides/scripts):** Otimize scripts de terceiros usando o componente Script, que adia automaticamente os scripts e impede que eles bloqueiem a thread principal.
- **[ESLint](/docs/architecture/accessibility#linting):** Use o plugin `eslint-plugin-jsx-a11y`, já incluído, para identificar problemas de acessibilidade logo no início.

### Segurança \{#security}

<AppOnly>

- **[Tainting](/docs/app/api-reference/config/next-config-js/taint):** Impeça que dados sensíveis sejam expostos ao cliente marcando objetos de dados e/ou valores específicos com taint.
- **[Server Actions](/docs/app/getting-started/mutating-data):** Verifique a autenticação e a autorização dentro de cada action. Não dependa apenas do Proxy ou de verificações no nível do layout ou da página. Mova o acesso ao banco de dados para uma [Data Access Layer](/docs/app/guides/data-security#data-access-layer) com `server-only` e considere [limitar a taxa de requisições](/docs/app/guides/backend-for-frontend#rate-limiting) em operações caras. Confira as [práticas de segurança recomendadas](/blog/security-nextjs-server-components-actions).

</AppOnly>

- **[Variáveis de ambiente](/docs/app/guides/environment-variables):** Confira se seus arquivos `.env.*` estão adicionados ao `.gitignore` e se apenas as variáveis públicas têm o prefixo `NEXT_PUBLIC_`.
- **[Content Security Policy](/docs/app/guides/content-security-policy):** Considere adicionar uma Content Security Policy para proteger seu app contra diversas ameaças de segurança, como cross-site scripting, clickjacking e outros ataques de injeção de código.

### Metadados e SEO \{#metadata-and-seo}

<AppOnly>

- **[Metadata API](/docs/app/getting-started/metadata-and-og-images):** Use a Metadata API para melhorar a otimização para mecanismos de busca (SEO) do seu app, adicionando títulos de página, descrições e outros dados.
- **[Imagens Open Graph (OG)](/docs/app/api-reference/file-conventions/metadata/opengraph-image):** Crie imagens OG para preparar seu app para o compartilhamento em redes sociais.
- **[Sitemaps](/docs/app/api-reference/functions/generate-sitemaps) e [Robots](/docs/app/api-reference/file-conventions/metadata/robots):** Ajude os mecanismos de busca a rastrear e indexar suas páginas gerando arquivos de sitemap e robots.

</AppOnly>

<PagesOnly>

- **[Componente `<Head>`](/docs/pages/api-reference/components/head):** Use o componente `next/head` para adicionar títulos de página, descrições e outros dados.

</PagesOnly>

### Segurança de tipos \{#type-safety}

- **TypeScript e [plugin do TS](/docs/app/api-reference/config/typescript):** Use TypeScript e o plugin do TypeScript para mais segurança de tipos e para identificar erros logo no início.

## Antes de ir para produção \{#before-going-to-production}

Antes de ir para produção, você pode rodar `next build` para fazer o build do seu app localmente e identificar erros de build, e depois rodar `next start` para medir a performance do seu app em um ambiente semelhante ao de produção.

### Core Web Vitals \{#core-web-vitals}

- **[Lighthouse](https://developers.google.com/web/tools/lighthouse):** Rode o Lighthouse em uma janela anônima para entender melhor como seus usuários vão experimentar seu site e para identificar pontos de melhoria. É um teste simulado, e deve ser combinado com a análise de dados de campo (como os Core Web Vitals).

<AppOnly>

- **[Hook `useReportWebVitals`](/docs/app/api-reference/functions/use-report-web-vitals):** Use este hook para enviar dados dos [Core Web Vitals](https://web.dev/articles/vitals) para ferramentas de analytics.

</AppOnly>

### Analisando bundles \{#analyzing-bundles}

Use o [plugin `@next/bundle-analyzer`](/docs/app/guides/package-bundling#nextbundle-analyzer-for-webpack) para analisar o tamanho dos seus bundles de JavaScript e identificar módulos e dependências grandes que possam estar impactando a performance do seu app.

Além disso, as ferramentas a seguir podem ajudar você a entender o impacto de adicionar novas dependências ao seu app:

- [Import Cost](https://marketplace.visualstudio.com/items?itemName=wix.vscode-import-cost)
- [Package Phobia](https://packagephobia.com/)
- [Bundle Phobia](https://bundlephobia.com/)
- [bundlejs](https://bundlejs.com/)
