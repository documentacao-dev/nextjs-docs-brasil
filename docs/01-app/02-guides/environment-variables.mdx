O Next.js tem suporte nativo a variáveis de ambiente, o que permite fazer o seguinte:

- [Usar `.env` para carregar variáveis de ambiente](#loading-environment-variables)
- [Incluir variáveis de ambiente no navegador prefixando com `NEXT_PUBLIC_`](#bundling-environment-variables-for-the-browser)

> **Aviso:** o template padrão do `create-next-app` adiciona todos os arquivos `.env` ao seu `.gitignore`. Você quase nunca quer commitar esses arquivos no repositório.

## Carregando variáveis de ambiente \{#loading-environment-variables}

O Next.js tem suporte nativo para carregar variáveis de ambiente dos arquivos `.env*` para o `process.env`.

```txt filename=".env"
DB_HOST=localhost
DB_USER=myuser
DB_PASS=mypassword
```

<PagesOnly>

Isso carrega `process.env.DB_HOST`, `process.env.DB_USER` e `process.env.DB_PASS` automaticamente no ambiente Node.js, permitindo usá-las nos [métodos de busca de dados do Next.js](/docs/pages/building-your-application/data-fetching) e nas [API routes](/docs/pages/building-your-application/routing/api-routes).

Por exemplo, usando [`getStaticProps`](/docs/pages/building-your-application/data-fetching/get-static-props):

```js filename="pages/index.js"
export async function getStaticProps() {
  const db = await myDB.connect({
    host: process.env.DB_HOST,
    username: process.env.DB_USER,
    password: process.env.DB_PASS,
  })
  // ...
}
```

</PagesOnly>

<AppOnly>

> **Observação**: o Next.js também oferece suporte a variáveis com múltiplas linhas dentro dos seus arquivos `.env*`:
>
> ```bash
> # .env
>
> # you can write with line breaks
> PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----
> ...
> Kh9NV...
> ...
> -----END DSA PRIVATE KEY-----"
>
> # or with `\n` inside double quotes
> PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----\nKh9NV...\n-----END DSA PRIVATE KEY-----\n"
> ```

> **Observação**: se você usa a pasta `/src`, saiba que o Next.js carrega os arquivos .env **somente** da pasta pai, e **não** da pasta `/src`.
> Isso carrega `process.env.DB_HOST`, `process.env.DB_USER` e `process.env.DB_PASS` automaticamente no ambiente Node.js, permitindo usá-las nos [Route Handlers](/docs/app/api-reference/file-conventions/route).

Por exemplo:

```js filename="app/api/route.js"
export async function GET() {
  const db = await myDB.connect({
    host: process.env.DB_HOST,
    username: process.env.DB_USER,
    password: process.env.DB_PASS,
  })
  // ...
}
```

</AppOnly>

### Carregando variáveis de ambiente com `@next/env` \{#loading-environment-variables-with-nextenv}

Se você precisar carregar variáveis de ambiente fora do runtime do Next.js, como em um arquivo de configuração raiz para um ORM ou um test runner, pode usar o pacote `@next/env`.

Esse pacote é usado internamente pelo Next.js para carregar variáveis de ambiente dos arquivos `.env*`.

Para usá-lo, instale o pacote e use a função `loadEnvConfig` para carregar as variáveis de ambiente:

```bash package="pnpm"
pnpm add @next/env
```

```bash package="npm"
npm install @next/env
```

```bash package="yarn"
yarn add @next/env
```

```bash package="bun"
bun add @next/env
```

```tsx filename="envConfig.ts" switcher
import { loadEnvConfig } from '@next/env'

const projectDir = process.cwd()
loadEnvConfig(projectDir)
```

```jsx filename="envConfig.js" switcher
import { loadEnvConfig } from '@next/env'

const projectDir = process.cwd()
loadEnvConfig(projectDir)
```

Depois, você pode importar a configuração onde for necessário. Por exemplo:

```tsx filename="orm.config.ts" switcher
import './envConfig.ts'

export default defineConfig({
  dbCredentials: {
    connectionString: process.env.DATABASE_URL!,
  },
})
```

```jsx filename="orm.config.js" switcher
import './envConfig.js'

export default defineConfig({
  dbCredentials: {
    connectionString: process.env.DATABASE_URL,
  },
})
```

### Referenciando outras variáveis \{#referencing-other-variables}

O Next.js expande automaticamente variáveis que usam `$` para referenciar outras variáveis, por exemplo `$VARIABLE`, dentro dos seus arquivos `.env*`. Isso permite referenciar outros segredos. Por exemplo:

```txt filename=".env"
TWITTER_USER=nextjs
TWITTER_URL=https://x.com/$TWITTER_USER
```

No exemplo acima, `process.env.TWITTER_URL` teria o valor `https://x.com/nextjs`.

> **Bom saber**: se você precisar usar uma variável com `$` no valor real, ela precisa ser escapada, por exemplo `\$`.

## Incluindo variáveis de ambiente para o navegador \{#bundling-environment-variables-for-the-browser}

Variáveis de ambiente que não começam com `NEXT_PUBLIC_` ficam disponíveis apenas no ambiente Node.js, ou seja, não são acessíveis no navegador (o cliente roda em um _ambiente_ diferente).

Para tornar o valor de uma variável de ambiente acessível no navegador, o Next.js pode "inserir" um valor no bundle JavaScript enviado ao cliente em tempo de build, substituindo todas as referências a `process.env.[variable]` por um valor fixo. Para isso, basta adicionar o prefixo `NEXT_PUBLIC_` à variável. Por exemplo:

```txt filename=".env"
NEXT_PUBLIC_ANALYTICS_ID=abcdefghijk
```

Isso faz o Next.js substituir todas as referências a `process.env.NEXT_PUBLIC_ANALYTICS_ID` no ambiente Node.js pelo valor do ambiente em que você executa `next build`, permitindo usá-la em qualquer lugar do seu código. Ela será inserida em todo JavaScript enviado ao navegador.

> **Observação**: depois do build, seu app não responderá mais a mudanças nessas variáveis de ambiente. Por exemplo, se você usa um pipeline do Heroku para promover slugs construídos em um ambiente para outro, ou se faz o build e o deploy de uma única imagem Docker para vários ambientes, todas as variáveis `NEXT_PUBLIC_` ficam congeladas com o valor avaliado no build. Por isso, esses valores precisam estar configurados corretamente quando o projeto for construído. Se você precisar de valores de ambiente em runtime, terá que criar sua própria API para fornecê-los ao cliente (sob demanda ou durante a inicialização).

```js filename="pages/index.js"
import setupAnalyticsService from '../lib/my-analytics-service'

// 'NEXT_PUBLIC_ANALYTICS_ID' can be used here as it's prefixed by 'NEXT_PUBLIC_'.
// It will be transformed at build time to `setupAnalyticsService('abcdefghijk')`.
setupAnalyticsService(process.env.NEXT_PUBLIC_ANALYTICS_ID)

function HomePage() {
  return <h1>Hello World</h1>
}

export default HomePage
```

Observe que buscas dinâmicas _não_ são inseridas no bundle, por exemplo:

```js
// This will NOT be inlined, because it uses a variable
const varName = 'NEXT_PUBLIC_ANALYTICS_ID'
setupAnalyticsService(process.env[varName])

// This will NOT be inlined, because it uses a variable
const env = process.env
setupAnalyticsService(env.NEXT_PUBLIC_ANALYTICS_ID)
```

### Variáveis de ambiente em runtime \{#runtime-environment-variables}

O Next.js aceita variáveis de ambiente de build time e de runtime.

**Por padrão, variáveis de ambiente ficam disponíveis apenas no servidor**. Para expor uma variável ao navegador, ela precisa ter o prefixo `NEXT_PUBLIC_`. No entanto, essas variáveis públicas são inseridas no bundle JavaScript durante o `next build`.

<PagesOnly>

Para ler variáveis de ambiente em runtime, recomendamos usar `getServerSideProps` ou [adotar o App Router de forma incremental](/docs/app/guides/migrating/app-router-migration).

</PagesOnly>

<AppOnly>

Você pode ler com segurança variáveis de ambiente no servidor durante a renderização dinâmica:

```tsx filename="app/page.ts" switcher
import { connection } from 'next/server'

export default async function Component() {
  await connection()
  // cookies, headers, and other Request-time APIs
  // will also opt into dynamic rendering, meaning
  // this env variable is evaluated at runtime
  const value = process.env.MY_VALUE
  // ...
}
```

```jsx filename="app/page.js" switcher
import { connection } from 'next/server'

export default async function Component() {
  await connection()
  // cookies, headers, and other Request-time APIs
  // will also opt into dynamic rendering, meaning
  // this env variable is evaluated at runtime
  const value = process.env.MY_VALUE
  // ...
}
```

</AppOnly>

Isso permite usar uma única imagem Docker que pode ser promovida entre vários ambientes com valores diferentes.

**Bom saber:**

- Você pode executar código na inicialização do servidor usando a [função `register`](/docs/app/guides/instrumentation).

## Variáveis de ambiente de teste \{#test-environment-variables}

Além dos ambientes `development` e `production`, existe uma terceira opção: `test`. Assim como você pode definir padrões para os ambientes de development ou production, também pode fazer isso com um arquivo `.env.test` para o ambiente de testes, embora ele seja menos comum que os outros dois. O Next.js não carrega variáveis de `.env.development` ou `.env.production` no ambiente de testes.

Isso é útil ao rodar testes com ferramentas como `jest` ou `cypress`, quando você precisa definir variáveis de ambiente específicas apenas para testes. Os valores padrão de teste são carregados se `NODE_ENV` for `test`, embora normalmente você não precise fazer isso manualmente, pois as ferramentas de teste cuidam disso para você.

Há uma pequena diferença entre o ambiente `test` e os ambientes `development` e `production` que você precisa ter em mente: `.env.local` não é carregado, pois você espera que os testes produzam os mesmos resultados para todos. Assim, cada execução de teste usa os mesmos valores padrão de ambiente, ignorando o `.env.local` (que serve para sobrescrever os padrões).

> **Bom saber**: assim como nas variáveis de ambiente padrão, o arquivo `.env.test` deve ser incluído no seu repositório, mas `.env.test.local` não, pois os arquivos `.env*.local` devem ser ignorados pelo `.gitignore`.

Ao rodar testes unitários, você pode garantir que as variáveis de ambiente sejam carregadas da mesma forma que o Next.js faz, usando a função `loadEnvConfig` do pacote `@next/env`.

```js
// The below can be used in a Jest global setup file or similar for your testing set-up
import { loadEnvConfig } from '@next/env'

export default async () => {
  const projectDir = process.cwd()
  loadEnvConfig(projectDir)
}
```

## Ordem de carregamento das variáveis de ambiente \{#environment-variable-load-order}

As variáveis de ambiente são procuradas nos lugares a seguir, nesta ordem, parando assim que a variável for encontrada:

1. `process.env`
1. `.env.$(NODE_ENV).local`
1. `.env.local` (Não verificado quando `NODE_ENV` é `test`.)
1. `.env.$(NODE_ENV)`
1. `.env`

Por exemplo, se `NODE_ENV` for `development` e você definir uma variável tanto em `.env.development.local` quanto em `.env`, o valor de `.env.development.local` será usado.

> **Bom saber**: os valores permitidos para `NODE_ENV` são `production`, `development` e `test`.

## Bom saber \{#good-to-know}

- Se você usa o [diretório `/src`](/docs/app/api-reference/file-conventions/src-folder), os arquivos `.env.*` devem continuar na raiz do projeto.
- Se a variável de ambiente `NODE_ENV` não estiver definida, o Next.js atribui automaticamente `development` ao executar o comando `next dev`, ou `production` em todos os outros comandos.
