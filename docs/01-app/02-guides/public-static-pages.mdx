Páginas públicas mostram o mesmo conteúdo para todos os usuários. Exemplos comuns incluem landing pages, páginas de marketing e páginas de produtos.

Como os dados são compartilhados, esses tipos de página podem ser [prerenderizados](/docs/app/glossary#prerendering) antecipadamente e reutilizados. Isso resulta em carregamentos de página mais rápidos e custos de servidor menores.

Este guia mostra como criar páginas públicas que compartilham dados entre usuários.

## Exemplo \{#example}

Como exemplo, vamos criar uma página de listagem de produtos.

Vamos começar com um cabeçalho estático, adicionar uma lista de produtos com dados externos assíncronos e aprender a renderizá-la sem bloquear a resposta. Por fim, vamos adicionar um banner de promoção específico do usuário, sem mudar a página inteira para a [renderização dinâmica](/docs/app/glossary#dynamic-rendering).

Você encontra os recursos usados neste exemplo aqui:

- [Vídeo](https://youtu.be/F6romq71KtI)
- [Demonstração](https://cache-components-public-pages.labs.vercel.dev/)
- [Código](https://github.com/nextjs/cache-components-public-pages)

### Passo 1: adicione um cabeçalho simples \{#step-1-add-a-simple-header}

Vamos começar com um cabeçalho simples.

```tsx filename="app/products/page.tsx"
// Static component
function Header() {
  return <h1>Shop</h1>
}

export default async function Page() {
  return (
    <>
      <Header />
    </>
  )
}
```

#### Componentes estáticos \{#static-components}

O componente `<Header />` não depende de nenhuma entrada que muda entre requisições, como dados externos, cabeçalhos de requisição, parâmetros de rota, a hora atual ou valores aleatórios.

> **Bom saber:** se você precisa exibir datas ou horários sensíveis ao locale sem um flash visível, veja [Evitando flash antes da hidratação](/docs/app/guides/preventing-flash-before-hydration).

Como a saída nunca muda e pode ser determinada antecipadamente, este tipo de componente é chamado de componente **estático**. Sem motivo para esperar uma requisição, o Next.js pode, com segurança, **prerenderizar** a página no [tempo de build](/docs/app/glossary#build-time).

Podemos confirmar isso executando o [`next build`](/docs/app/api-reference/cli/next#next-build-options).

```bash filename="Terminal"
Route (app)      Revalidate  Expire
┌ ○ /products           15m      1y
└ ○ /_not-found

○  (Static)  prerendered as static content
```

Observe que a rota de produtos está marcada como estática, mesmo sem nenhuma configuração explícita que tenhamos adicionado.

### Passo 2: adicione a lista de produtos \{#step-2-add-the-product-list}

Agora, vamos buscar e renderizar a nossa lista de produtos.

```tsx filename="app/products/page.tsx"
import db from '@/db'
import { List } from '@/app/products/ui'

function Header() {}

// Dynamic component
async function ProductList() {
  const products = await db.product.findMany()
  return <List items={products} />
}

export default async function Page() {
  return (
    <>
      <Header />
      <ProductList />
    </>
  )
}
```

Diferente do cabeçalho, a lista de produtos depende de dados externos.

#### Componentes dinâmicos \{#dynamic-components}

Como esses dados **podem** mudar com o tempo, a saída renderizada não é mais garantidamente estável. Isso torna a lista de produtos um componente **dinâmico**.

Sem orientação, o framework assume que você quer buscar dados **novos** a cada requisição do usuário. Essa escolha de design reflete o comportamento padrão da web, em que uma nova requisição ao servidor renderiza a página.

No entanto, se esse componente for renderizado no momento da requisição, buscar os dados dele vai atrasar a resposta da rota **inteira**. Se atualizarmos a página, podemos ver isso acontecer.

Mesmo que o cabeçalho seja renderizado instantaneamente, ele não pode ser enviado ao navegador até que a lista de produtos termine de buscar os dados.

Para nos proteger desse gargalo de desempenho, a primeira vez que fizermos **await** nesses dados sem cache, o Next.js mostra um [aviso](/docs/messages/blocking-prerender-dynamic): acessar dados sem cache fora de `<Suspense>` impede que a rota seja prerenderizada.

Neste ponto, precisamos decidir como **desbloquear** a resposta. Podemos:

- [**Armazenar em cache**](/docs/app/glossary#cache-components) o componente, para que ele se torne **estável** e possa ser prerenderizado junto com o restante da página.
- Usar [**streaming**](/docs/app/glossary#streaming) no componente, para que ele se torne **não bloqueante** e o restante da página não precise esperar por ele.

No nosso caso, o catálogo de produtos é compartilhado por todos os usuários, então armazenar em cache é a escolha certa.

### Cache components \{#cache-components}

Podemos marcar uma função como armazenável em cache usando a diretiva [`'use cache'`](/docs/app/api-reference/directives/use-cache).

```tsx filename="app/products/page.tsx"
import db from '@/db'
import { List } from '@/app/products/ui'

function Header() {}

// Cache component
async function ProductList() {
  'use cache'
  const products = await db.product.findMany()
  return <List items={products} />
}

export default async function Page() {
  return (
    <>
      <Header />
      <ProductList />
    </>
  )
}
```

Isso transforma a função em um [cache component](/docs/app/glossary#cache-components). Na primeira vez que ela roda, o que retornarmos será armazenado em cache e reutilizado.

Se as entradas de um cache component estiverem disponíveis **antes** de a requisição chegar, ele pode ser prerenderizado da mesma forma que um componente estático.

Se atualizarmos novamente, podemos ver que a página carrega instantaneamente, porque o cache component não bloqueia a resposta. E, se executarmos `next build` de novo, podemos confirmar que a página continua estática:

```bash filename="Terminal"
Route (app)      Revalidate  Expire
┌ ○ /products           15m      1y
└ ○ /_not-found

○  (Static)  prerendered as static content
```

Mas as páginas raramente continuam estáticas para sempre.

### Passo 3: adicione um banner de promoção dinâmico \{#step-3-add-a-dynamic-promotion-banner}

Mais cedo ou mais tarde, até páginas simples precisam de algum conteúdo dinâmico. Para demonstrar isso, vamos adicionar um banner promocional:

```tsx filename="app/products/page.tsx"
import db from '@/db'
import { List, Promotion } from '@/app/products/ui'
import { getPromotion } from '@/app/products/data'

function Header() {}

async function ProductList() {}

// Dynamic component
async function PromotionContent() {
  const promotion = await getPromotion()
  return <Promotion data={promotion} />
}

export default async function Page() {
  return (
    <>
      <PromotionContent />
      <Header />
      <ProductList />
    </>
  )
}
```

Mais uma vez, isso começa como dinâmico. E, como antes, introduzir comportamento de bloqueio dispara um aviso do Next.js.

Da última vez, os dados eram compartilhados, então podiam ser armazenados em cache. Desta vez, a promoção depende de entradas específicas da requisição, como a localização do usuário e testes A/B, então não conseguimos resolver o comportamento de bloqueio com cache.

### Partial prerendering \{#partial-prerendering}

Adicionar conteúdo dinâmico não significa que precisamos voltar a uma renderização totalmente bloqueante. Podemos desbloquear a resposta com streaming.

O Next.js já faz streaming por padrão. Podemos usar uma [fronteira do Suspense](/docs/app/glossary#suspense-boundary) para indicar ao framework onde dividir a resposta em _partes_ e qual UI de fallback mostrar enquanto o conteúdo carrega.

```tsx filename="app/products/page.tsx"
import { Suspense } from 'react'
import db from '@/db'
import { List, Promotion, PromotionSkeleton } from '@/app/products/ui'
import { getPromotion } from '@/app/products/data'

function Header() {}

async function ProductList() {}

// Dynamic component (streamed)
async function PromotionContent() {
  const promotion = await getPromotion()
  return <Promotion data={promotion} />
}

export default async function Page() {
  return (
    <>
      <Suspense fallback={<PromotionSkeleton />}>
        <PromotionContent />
      </Suspense>
      <Header />
      <ProductList />
    </>
  )
}
```

O fallback é prerenderizado junto com o restante do nosso conteúdo estático e em cache. O componente interno chega em streaming depois, quando o trabalho assíncrono dele termina.

Com essa mudança, o Next.js consegue separar o trabalho prerenderizável do trabalho do momento da requisição, e a rota se torna [parcialmente prerenderizada](/docs/app/glossary#partial-prerendering-ppr).

Mais uma vez, podemos confirmar isso executando `next build`:

```bash filename="Terminal"
Route (app)      Revalidate  Expire
┌ ◐ /products    15m      1y
└ ◐ /_not-found

◐  (Partial Prerender)  Prerendered as static HTML with dynamic server-streamed content
```

No [**tempo de build**](/docs/app/glossary#build-time), a maior parte da página, incluindo o cabeçalho, a lista de produtos e o fallback da promoção, é renderizada, armazenada em cache e enviada para uma rede de distribuição de conteúdo (CDN).

No [**momento da requisição**](/docs/app/glossary#dynamic-rendering), a parte prerenderizada é servida instantaneamente a partir de um nó de CDN próximo ao usuário.

Em paralelo, a promoção específica do usuário é renderizada no servidor, enviada em streaming ao cliente e trocada pelo slot do fallback.

Se atualizarmos a página mais uma vez, podemos ver que a maior parte dela carrega instantaneamente, enquanto as partes dinâmicas chegam em streaming conforme ficam disponíveis.
