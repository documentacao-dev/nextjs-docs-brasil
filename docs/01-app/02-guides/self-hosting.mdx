Ao [fazer o deploy](/docs/app/getting-started/deploying) do seu app Next.js, talvez queira configurar como diferentes funcionalidades são tratadas de acordo com a sua infraestrutura.

## Proxy reverso \{#reverse-proxy}

Ao fazer self-hosting, é recomendado usar um proxy reverso (como o nginx) na frente do servidor Next.js, em vez de expô-lo diretamente à internet. Um proxy reverso pode lidar com requisições malformadas, ataques de conexão lenta, limites de tamanho de payload, rate limiting e outras questões de segurança, tirando essas tarefas do servidor Next.js. Assim, o servidor pode dedicar seus recursos à renderização, e não à validação de requisições.

## Otimização de imagens \{#image-optimization}

A [otimização de imagens](/docs/app/api-reference/components/image) feita pelo `next/image` funciona em self-hosting sem nenhuma configuração ao fazer deploy com `next start`. Se você preferir ter um serviço separado para otimizar imagens, pode [configurar um image loader](/docs/app/api-reference/components/image#loader).

A otimização de imagens pode ser usada com uma [exportação estática](/docs/app/guides/static-exports#image-optimization) definindo um image loader personalizado em `next.config.js`. Observe que as imagens são otimizadas em runtime, e não durante o build.

> **Bom saber:**
>
> - Em sistemas Linux baseados em glibc, a otimização de imagens pode exigir [configuração adicional](https://sharp.pixelplumbing.com/install#linux-memory-allocator) para evitar uso excessivo de memória.
> - Saiba mais sobre o [comportamento de cache das imagens otimizadas](/docs/app/api-reference/components/image#minimumcachettl) e como configurar o TTL.
> - Se preferir, você também pode [desativar a otimização de imagens](/docs/app/api-reference/components/image#unoptimized) e continuar aproveitando outros benefícios do `next/image`. Por exemplo, se você otimiza as imagens por conta própria, separadamente.

## Proxy \{#proxy}

O [Proxy](/docs/app/api-reference/file-conventions/proxy) funciona em self-hosting sem nenhuma configuração ao fazer deploy com `next start`. Como ele precisa acessar a requisição recebida, não é aceito ao usar uma [exportação estática](/docs/app/guides/static-exports).

Se você quer adicionar lógica (ou usar um pacote externo) que exige todas as APIs do Node.js, talvez seja possível mover essa lógica para um [layout](/docs/app/api-reference/file-conventions/layout) como um [Server Component](/docs/app/getting-started/server-and-client-components). Por exemplo, verificar [headers](/docs/app/api-reference/functions/headers) e [redirecionar](/docs/app/api-reference/functions/redirect). Você também pode usar headers, cookies ou query parameters para [redirecionar](/docs/app/api-reference/config/next-config-js/redirects#header-cookie-and-query-matching) ou [reescrever](/docs/app/api-reference/config/next-config-js/rewrites#header-cookie-and-query-matching) por meio do `next.config.js`. Se isso não funcionar, também é possível usar um [servidor personalizado](/docs/pages/guides/custom-server).

## Variáveis de ambiente \{#environment-variables}

O Next.js aceita variáveis de ambiente tanto em tempo de build quanto em runtime.

**Por padrão, as variáveis de ambiente só ficam disponíveis no servidor**. Para expor uma variável de ambiente ao navegador, ela precisa ter o prefixo `NEXT_PUBLIC_`. No entanto, essas variáveis públicas serão incorporadas (inlined) ao bundle JavaScript durante o `next build`.

<PagesOnly>

Para ler variáveis de ambiente de runtime, recomendamos usar `getServerSideProps` ou [adotar o App Router de forma incremental](/docs/app/guides/migrating/app-router-migration).

</PagesOnly>

<AppOnly>

Você lê variáveis de ambiente com segurança no servidor durante a renderização dinâmica.

```tsx filename="app/page.ts" switcher
import { connection } from 'next/server'

export default async function Component() {
  await connection()
  // cookies, headers, and other Request-time APIs
  // will also opt into dynamic rendering, meaning
  // this env variable is evaluated at runtime
  const value = process.env.MY_VALUE
  // ...
}
```

```jsx filename="app/page.js" switcher
import { connection } from 'next/server'

export default async function Component() {
  await connection()
  // cookies, headers, and other Request-time APIs
  // will also opt into dynamic rendering, meaning
  // this env variable is evaluated at runtime
  const value = process.env.MY_VALUE
  // ...
}
```

</AppOnly>

Isso permite usar uma única imagem Docker que pode ser promovida entre vários ambientes com valores diferentes.

> **Bom saber:**
>
> - Você pode executar código na inicialização do servidor usando a [função `register`](/docs/app/guides/instrumentation).

## Cache e ISR \{#caching-and-isr}

O Next.js pode armazenar em cache respostas, páginas estáticas geradas, outputs de build e outros assets estáticos, como imagens, fontes e scripts.

O cache de páginas e de dados revalidados (com a [Incremental Static Regeneration](/docs/app/guides/incremental-static-regeneration)) usa o **mesmo cache do servidor do Next.js**. Por padrão, esse cache é armazenado no sistema de arquivos local (em disco) de cada instância do servidor Next.js.

Isso funciona automaticamente para uma única instância hospedada por você com `next start` e disco local persistente. Se você executar várias instâncias, usar compute efêmero ou colocar um CDN/proxy reverso na frente do Next.js, revise também [Configurar o cache](#configuring-caching), [Coordenação de cache entre múltiplas instâncias](#multi-instance-cache-coordination) e [Uso com CDNs](#usage-with-cdns).

Você pode configurar o local de cache do Next.js se quiser persistir páginas e dados em cache em um armazenamento durável, ou compartilhar o cache entre vários containers ou instâncias do seu app Next.js.

### Cache automático \{#automatic-caching}

- O Next.js define o header `Cache-Control` como `public, max-age=31536000, immutable` para assets verdadeiramente imutáveis. Esse valor não pode ser sobrescrito. Esses arquivos imutáveis contêm um hash SHA no nome, então podem ser armazenados em cache por tempo indefinido com segurança. Por exemplo, [importações estáticas de imagens](/docs/app/getting-started/images#local-images). Você pode [configurar o TTL](/docs/app/api-reference/components/image#minimumcachettl) das imagens.
- A Incremental Static Regeneration (ISR) define o header `Cache-Control` como `s-maxage: <revalidate in getStaticProps>, stale-while-revalidate`. Esse tempo de revalidação é definido na sua [função `getStaticProps`](/docs/pages/building-your-application/data-fetching/get-static-props) em segundos. Se você definir `revalidate: false`, será usada por padrão uma duração de cache de um ano. Para aproveitar isso na camada do CDN, seu CDN/proxy reverso precisa respeitar essas diretivas e a variabilidade da chave de cache ([Cache de CDN](/docs/app/guides/cdn-caching)); caso contrário, as respostas podem ignorar o cache do CDN ou servir variantes desatualizadas ou incompatíveis durante a navegação no cliente.
- Páginas renderizadas dinamicamente definem o header `Cache-Control` como `private, no-cache, no-store, max-age=0, must-revalidate` para impedir que dados específicos do usuário sejam armazenados em cache. Isso vale tanto para o App Router quanto para o Pages Router. Também inclui o [Draft Mode](/docs/app/guides/draft-mode).

### Assets estáticos \{#static-assets}

Se você quiser hospedar assets estáticos em um domínio ou CDN diferente, pode usar a [configuração](/docs/app/api-reference/config/next-config-js/assetPrefix) `assetPrefix` em `next.config.js`. O Next.js vai usar esse prefixo de asset ao buscar arquivos JavaScript ou CSS. Separar os assets em outro domínio tem a desvantagem de consumir mais tempo com resolução de DNS e TLS.

[Saiba mais sobre `assetPrefix`](/docs/app/api-reference/config/next-config-js/assetPrefix).

### Configurar o cache \{#configuring-caching}

Por padrão, os assets de cache gerados são armazenados em memória (o padrão é 50 MB) e em disco. Em plataformas de compute efêmero (configurações serverless comuns), o disco local frequentemente não é persistente ou não está disponível, então esse cache é, na prática, de curta duração e restrito a cada instância. Se você hospeda o Next.js em uma plataforma de orquestração de containers, como o Kubernetes, cada pod terá uma cópia do cache. Para evitar que dados desatualizados sejam exibidos, já que o cache não é compartilhado entre pods por padrão, você pode configurar o Next.js para usar um cache handler e desativar o cache em memória.

Para configurar o local do cache ao fazer self-hosting, defina um handler personalizado no seu arquivo `next.config.js`:

```jsx filename="next.config.js"
module.exports = {
  cacheHandler: require.resolve('./cache-handler.js'),
  cacheMaxMemorySize: 0, // disable default in-memory caching
}
```

O arquivo do handler exporta uma classe que implementa `get`, `set`, `revalidateTag` e `resetRequestCache`. Consulte [`cacheHandler`](/docs/app/api-reference/config/next-config-js/incrementalCacheHandlerPath) para a assinatura de cada método, e o [exemplo de `cacheHandler` com Redis](https://github.com/vercel/next.js/tree/canary/examples/cache-handler-redis) para uma implementação funcional.

Em implantações de produção, o handler precisa:

- **Armazenar as entradas em um lugar que todas as instâncias consigam acessar**, como [Redis](https://github.com/vercel/next.js/tree/canary/examples/cache-handler-redis) ou AWS S3. Um armazenamento dentro do processo, como um `Map`, faz com que cada pod tenha novamente sua própria cópia do cache.
- **Limitar o tamanho do armazenamento.** Use um TTL ou uma remoção baseada em tamanho para eliminar entradas de caminhos e chaves de `fetch` que não são mais requisitados.
- **Serializar as entradas.** Qualquer armazenamento fora do processo precisa disso. Uma entrada pode conter valores `Buffer` (por exemplo, `rscData`) e `Map` (por exemplo, `segmentData`) que `JSON.stringify`/`JSON.parse` não conseguem serializar e restaurar sozinhos. Não tratar essa serialização resulta em erros como `segmentData.get is not a function` ou `failed to pipe response` na navegação no cliente ou em requisições de prefetch (RSC).
- **Indexar as entradas por tag.** As entradas `APP_PAGE`, `APP_ROUTE` e `PAGES` carregam suas tags no header de resposta `x-next-cache-tags` (`data.headers`), enquanto `ctx.tags` carrega as tags das entradas de `fetch`. Mantenha o índice no armazenamento compartilhado, para que uma chamada de `revalidateTag` em uma instância invalide a entrada em todas as instâncias.
- **Tratar erros de armazenamento**, como timeouts e conexões interrompidas.

> **Bom saber:**
>
> - `revalidatePath` é uma camada de conveniência sobre as tags de cache. Chamar `revalidatePath` vai chamar a função `revalidateTag` com uma tag padrão especial para a página informada.
> - Se você estiver configurando backends para diretivas `'use cache'`, use [`cacheHandlers`](/docs/app/api-reference/config/next-config-js/cacheHandlers).
> - Handlers Redis da comunidade voltados para produção (timeouts de GET, coalescência em memória, coordenação de tags entre instâncias) estão listados no [README do exemplo com Redis](https://github.com/vercel/next.js/blob/canary/examples/cache-handler-redis/README.md#production-community-handlers), incluindo [`@trieb.work/nextjs-turbo-redis-cache`](https://github.com/trieb-work/nextjs-turbo-redis-cache) e [`@mrjasonroy/cache-components-cache-handler`](https://github.com/mrjasonroy/cache-components-cache-handler).

## Cache de build \{#build-cache}

O Next.js gera um ID durante o `next build` para identificar qual versão do seu app está sendo servida. O mesmo build deve ser usado para subir vários containers.

Se você fizer um novo build para cada estágio do seu ambiente, precisará gerar um ID de build consistente para usar entre os containers. Use a opção `generateBuildId` em `next.config.js`:

```jsx filename="next.config.js"
module.exports = {
  generateBuildId: async () => {
    // This could be anything, using the latest git hash
    return process.env.GIT_HASH
  },
}
```

> **Bom saber:** quando [`deploymentId`](/docs/app/api-reference/config/next-config-js/deploymentId) está definido, o Next.js usa um ID de build constante, a menos que você configure explicitamente o `generateBuildId`. A [divergência de versões](#version-skew) é detectada a partir do ID de deploy.

## Deploys com múltiplos servidores \{#multi-server-deployments}

Ao executar o Next.js em várias instâncias de servidor (por exemplo, containers atrás de um load balancer), há considerações adicionais para garantir um comportamento consistente.

### Chave de criptografia das Server Functions \{#server-functions-encryption-key}

O Next.js criptografa as variáveis de closure das [Server Functions](/docs/app/getting-started/mutating-data) antes de enviá-las ao cliente. Por padrão, uma chave de criptografia exclusiva é gerada para cada build.

Ao executar várias instâncias de servidor, todas precisam usar a mesma chave de criptografia. Caso contrário, uma Server Function criptografada por uma instância não pode ser descriptografada por outra, o que causa erros "Failed to find Server Action".

Defina uma chave de criptografia consistente usando a variável de ambiente `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`. A chave precisa ser um valor codificado em base64 com um tamanho válido de chave AES (16, 24 ou 32 bytes). O Next.js gera chaves de 32 bytes por padrão.

```bash
NEXT_SERVER_ACTIONS_ENCRYPTION_KEY=your-generated-key next build
```

A chave fica incorporada ao output do build e é usada automaticamente em runtime. Saiba mais no [guia de Segurança de dados](/docs/app/guides/data-security#overwriting-encryption-keys-advanced).

### Identificador de deploy \{#deployment-identifier}

Configure um [`deploymentId`](/docs/app/api-reference/config/next-config-js/deploymentId) para ativar a proteção contra divergência de versões durante deploys graduais (rolling deployments). Isso garante que os clientes sempre recebam assets de uma mesma versão de deploy.

### Cache compartilhado \{#shared-cache}

Por padrão, o Next.js usa um cache em memória que não é compartilhado entre instâncias. Para um comportamento de cache consistente, use [`'use cache: remote'`](/docs/app/api-reference/directives/use-cache-remote) com um [handler de cache personalizado](/docs/app/api-reference/config/next-config-js/cacheHandlers) que armazena os dados em um armazenamento externo.

## Divergência de versões \{#version-skew}

Ao fazer self-hosting em várias instâncias ou em deploys graduais, a [divergência de versões (version skew)](/docs/app/glossary#version-skew) pode causar:

- **Assets ausentes**: o cliente pede arquivos JavaScript ou CSS que não existem mais no servidor
- **Incompatibilidades de Server Functions**: o cliente invoca uma Server Function usando um ID de um build anterior que o servidor não reconhece mais
- **Falhas de navegação**: dados de páginas com prefetch de um deploy antigo são incompatíveis com o novo servidor

O Next.js usa o [`deploymentId`](/docs/app/api-reference/config/next-config-js/deploymentId) para detectar e tratar a divergência de versões. Quando um ID de deploy está configurado:

- Os assets estáticos incluem um parâmetro de query `?dpl=<deploymentId>`
- As requisições de navegação no cliente incluem um header `x-deployment-id`
- O servidor compara o ID de deploy do cliente com o próprio

Se uma divergência for detectada, o Next.js dispara uma navegação completa (recarregamento total da página) em vez de uma navegação no cliente. Assim, o cliente busca os assets de uma mesma versão de deploy.

```js filename="next.config.js"
module.exports = {
  deploymentId: process.env.DEPLOYMENT_VERSION,
}
```

> **Bom saber:** quando o app é recarregado, o estado dele pode ser perdido se ele não foi projetado para persistir entre navegações de página. O estado na URL ou no local storage seria mantido, mas o estado de componentes, como o `useState`, seria perdido.

### Assets imutáveis \{#immutable-assets}

Ao usar [assets estáticos imutáveis](/docs/app/api-reference/config/next-config-js/supportsImmutableAssets), evitar a divergência de versões fica muito mais fácil:

Os assets podem ser compartilhados entre deploys, então, se você apenas continuar adicionando-os à sua pasta de arquivos estáticos existente (ou ao bucket do CDN), não haverá divergência de versões (sem precisar rastrear IDs de deploy no proxy reverso nem fazer deploys blue-green).

## Streaming e Suspense \{#streaming-and-suspense}

O App Router do Next.js aceita [respostas em streaming](/docs/app/api-reference/file-conventions/loading) quando hospedado por você. Se você usa nginx ou um proxy semelhante, será necessário configurá-lo para desativar o buffering e permitir o streaming.

Por exemplo, você pode desativar o buffering no nginx definindo `X-Accel-Buffering` como `no`:

```js filename="next.config.js"
module.exports = {
  async headers() {
    return [
      {
        source: '/:path*{/}?',
        headers: [
          {
            key: 'X-Accel-Buffering',
            value: 'no',
          },
        ],
      },
    ]
  },
}
```

Além do nginx, verifique se toda a sua infraestrutura aceita streaming de ponta a ponta:

- **Load balancers** precisam aceitar chunked transfer encoding ou streaming HTTP/2. Alguns load balancers em nuvem (por exemplo, o AWS ALB com integração com Lambda) podem fazer buffer das respostas por padrão.
- **Proxies reversos** entre o load balancer e o Next.js também precisam repassar respostas em chunks sem fazer buffer.
- Se estiver usando [Partial Prerendering](/docs/app/guides/ppr-platform-guide), o suporte a streaming é obrigatório. Sem ele, o shell estático e o conteúdo dinâmico são entregues juntos somente depois que a renderização completa termina, eliminando a vantagem de time-to-first-byte do PPR.

## Coordenação de cache entre múltiplas instâncias \{#multi-instance-cache-coordination}

Além da [configuração de múltiplos servidores](/docs/app/guides/self-hosting#multi-server-deployments) acima (chave de criptografia, ID de deploy, cache compartilhado), deploys do App Router com várias instâncias precisam de coordenação das tags de cache.

Por padrão, chamar [`revalidateTag()`](/docs/app/api-reference/functions/revalidateTag) em uma instância invalida o cache apenas nessa instância. As outras instâncias continuam servindo conteúdo desatualizado até descobrirem a invalidação por conta própria.

Para coordenar a invalidação de tags entre instâncias, implemente o método [`refreshTags()`](/docs/app/api-reference/config/next-config-js/cacheHandlers#refreshtags) no seu [handler de cache personalizado](/docs/app/api-reference/config/next-config-js/cacheHandlers). Esse método é chamado antes de cada requisição e deve sincronizar o estado das tags a partir de um armazenamento compartilhado (como o Redis), para que todas as instâncias fiquem sabendo das invalidações rapidamente.

Para uma explicação detalhada da arquitetura de tags, veja [Como funciona a revalidação](/docs/app/guides/how-revalidation-works).

## Cache Components \{#cache-components}

[Cache Components](/docs/app/getting-started/caching) funciona por padrão com o Next.js e não é um recurso exclusivo de CDN. Isso inclui o deploy como servidor Node.js (com `next start`) e o uso com um container Docker.

## Uso com CDNs \{#usage-with-cdns}

Ao usar um CDN na frente do seu app Next.js, a página incluirá o header de resposta `Cache-Control: private` quando APIs dinâmicas forem acessadas. Isso garante que a página HTML resultante seja marcada como não armazenável em cache. Se a página for totalmente prerendered como estática, ela incluirá `Cache-Control: public` para permitir que seja armazenada em cache no CDN.

Se você não precisa de uma mistura de componentes estáticos e dinâmicos, pode tornar toda a rota estática e armazenar o HTML de saída em um CDN. Essa Automatic Static Optimization é o comportamento padrão ao executar `next build` quando APIs dinâmicas não são usadas.

Para orientações detalhadas sobre o comportamento de cache em CDNs, degradação graciosa e variabilidade de cache, veja [Cache de CDN](/docs/app/guides/cdn-caching). Para saber quais plataformas aceitam Partial Prerendering, veja o [Guia de PPR para plataformas](/docs/app/guides/ppr-platform-guide) e a [Deployment Adapter API](/docs/app/api-reference/config/next-config-js/adapterPath).

</AppOnly>

## `after` \{#after}

[`after`](/docs/app/api-reference/functions/after) funciona totalmente ao fazer self-hosting com `next start`.

Ao parar o servidor, faça um encerramento gracioso enviando os sinais `SIGINT` ou `SIGTERM` e aguardando. O servidor do Next.js vai concluir as requisições em andamento e executar quaisquer callbacks `after()` pendentes antes de encerrar. As plataformas devem permitir um período de drenagem configurável (recomendamos entre 10 e 30 segundos) para garantir que todo o trabalho em segundo plano seja concluído.

</AppOnly>

<PagesOnly>

## Encerramento gracioso manual \{#manual-graceful-shutdowns}

Ao fazer self-hosting, você pode querer executar código quando o servidor for encerrado com os sinais `SIGTERM` ou `SIGINT`.

Você pode definir a variável de ambiente `NEXT_MANUAL_SIG_HANDLE` como `true` e depois registrar um handler para esse sinal dentro do seu arquivo `_document.js`. Você precisará definir a variável de ambiente diretamente no script do `package.json`, e não no arquivo `.env`.

> **Bom saber**: o tratamento manual de sinais não está disponível em `next dev`.

```json filename="package.json"
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "NEXT_MANUAL_SIG_HANDLE=true next start"
  }
}
```

```js filename="pages/_document.js"
if (process.env.NEXT_MANUAL_SIG_HANDLE) {
  process.on('SIGTERM', () => {
    console.log('Received SIGTERM: cleaning up')
    process.exit(0)
  })
  process.on('SIGINT', () => {
    console.log('Received SIGINT: cleaning up')
    process.exit(0)
  })
}
```

</PagesOnly>
