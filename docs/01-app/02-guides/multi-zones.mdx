Multi-Zones são uma abordagem de micro-frontends que separa um app grande em um domínio em apps Next.js menores, cada um atendendo a um conjunto de caminhos. Isso é útil quando há coleções de páginas sem relação com as demais páginas do app. Ao mover essas páginas para uma zone separada (ou seja, um app separado), você reduz o tamanho de cada app, o que melhora os tempos de build e remove o código que só é necessário para uma das zones. Como os apps são desacoplados, Multi-Zones também permite que outros apps no domínio usem o framework de sua escolha.

Por exemplo, digamos que você tenha o seguinte conjunto de páginas que gostaria de dividir:

- `/blog/*` para todos os posts do blog
- `/dashboard/*` para todas as páginas quando o usuário está logado no dashboard
- `/*` para o restante do site que não é coberto por outras zones

Com Multi-Zones, você pode criar três apps que são todos servidos no mesmo domínio e têm a mesma aparência para o usuário, mas você pode desenvolver e fazer deploy de cada um deles de forma independente.

Navegar entre páginas da mesma zone realiza navegações suaves, uma navegação que não exige recarregar a página. Por exemplo, neste diagrama, navegar de `/` para `/products` é uma navegação suave.

Navegar de uma página em uma zone para uma página em outra zone, como de `/` para `/dashboard`, realiza uma navegação completa, descarregando os recursos da página atual e carregando os recursos da nova página. Páginas que são visitadas com frequência juntas devem ficar na mesma zone para evitar navegações completas.

## Como definir uma zone \{#how-to-define-a-zone}

Uma zone é um app Next.js normal em que você também configura um [assetPrefix](/docs/app/api-reference/config/next-config-js/assetPrefix) para evitar conflitos com páginas e arquivos estáticos de outras zones.

```js filename="next.config.js"
/** @type {import('next').NextConfig} */
const nextConfig = {
  assetPrefix: '/blog-static',
}
```

Os assets do Next.js, como JavaScript e CSS, terão o `assetPrefix` como prefixo para garantir que não entrem em conflito com os assets de outras zones. Esses assets são servidos em `/assetPrefix/_next/...` para cada uma das zones.

O app padrão, que trata todos os caminhos não roteados para uma zone mais específica, não precisa de `assetPrefix`.

Em versões anteriores ao Next.js 15, você pode precisar de um rewrite adicional para tratar os arquivos estáticos. Isso não é mais necessário no Next.js 15.

```js filename="next.config.js"
/** @type {import('next').NextConfig} */
const nextConfig = {
  assetPrefix: '/blog-static',
  async rewrites() {
    return {
      beforeFiles: [
        {
          source: '/blog-static/_next/:path+',
          destination: '/_next/:path+',
        },
      ],
    }
  },
}
```

## Como rotear requisições para a zone certa \{#how-to-route-requests-to-the-right-zone}

Com a configuração de Multi Zones, você precisa rotear os caminhos para a zone correta, já que eles são servidos por apps diferentes. Você pode usar qualquer proxy HTTP para isso, mas um dos apps Next.js também pode ser usado para rotear as requisições de todo o domínio.

Para rotear para a zone correta usando um app Next.js, você pode usar os [`rewrites`](/docs/app/api-reference/config/next-config-js/rewrites). Para cada caminho servido por uma zone diferente, adicione uma regra de rewrite que envie esse caminho para o domínio da outra zone, e também reescreva as requisições dos arquivos estáticos. Por exemplo:

```js filename="next.config.js"
async rewrites() {
    return [
        {
            source: '/blog',
            destination: `${process.env.BLOG_DOMAIN}/blog`,
        },
        {
            source: '/blog/:path+',
            destination: `${process.env.BLOG_DOMAIN}/blog/:path+`,
        },
        {
            source: '/blog-static/:path+',
            destination: `${process.env.BLOG_DOMAIN}/blog-static/:path+`,
        }
    ];
}
```

`destination` deve ser uma URL servida pela zone, incluindo esquema e domínio. Ela deve apontar para o domínio de produção da zone, mas também pode ser usada para rotear requisições para `localhost` no desenvolvimento local.

> **Bom saber**: os caminhos de URL devem ser únicos em cada zone. Por exemplo, duas zones tentando servir `/blog` criariam um conflito de roteamento.

### Roteando requisições usando proxy \{#routing-requests-using-proxy}

Rotear requisições pelos [`rewrites`](/docs/app/api-reference/config/next-config-js/rewrites) é recomendado para minimizar a latência extra das requisições, mas o proxy também pode ser usado quando é preciso uma decisão dinâmica no roteamento. Por exemplo, se você usa uma feature flag para decidir para onde um caminho deve ser roteado, como durante uma migração, pode usar o proxy.

```js filename="proxy.js"
export async function proxy(request) {
  const { pathname, search } = request.nextUrl
  if (pathname === '/your-path' && myFeatureFlag.isEnabled()) {
    return NextResponse.rewrite(`${rewriteDomain}${pathname}${search}`)
  }
}
```

## Links entre zones \{#linking-between-zones}

Links para caminhos de outra zone devem usar uma tag `a` em vez do componente [`<Link>`](/docs/app/api-reference/components/link) do Next.js. Isso acontece porque o Next.js tenta fazer prefetch e navegação suave para qualquer caminho relativo no componente `<Link>`, o que não funciona entre zones.

## Compartilhando código \{#sharing-code}

Os apps Next.js que compõem as diferentes zones podem morar em qualquer repositório. No entanto, costuma ser conveniente colocar essas zones em um [monorepo](https://en.wikipedia.org/wiki/Monorepo) para compartilhar código com mais facilidade. Para zones que moram em repositórios diferentes, o código também pode ser compartilhado usando pacotes NPM públicos ou privados.

Como as páginas de zones diferentes podem ser lançadas em momentos diferentes, feature flags podem ser úteis para ativar ou desativar recursos em conjunto nas diferentes zones.

## Server Actions \{#server-actions}

Ao usar [Server Actions](/docs/app/getting-started/mutating-data) com Multi-Zones, você deve permitir explicitamente a origem voltada ao usuário, já que o domínio voltado ao usuário pode servir vários apps. No seu arquivo `next.config.js`, adicione as seguintes linhas:

```js filename="next.config.js"
const nextConfig = {
  experimental: {
    serverActions: {
      allowedOrigins: ['your-production-domain.com'],
    },
  },
}
```

Veja [`experimental.serverActions.allowedOrigins`](/docs/app/api-reference/config/next-config-js/serverActions#allowedorigins) para mais informações.
