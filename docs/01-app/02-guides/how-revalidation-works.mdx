A página de [Cache](/docs/app/getting-started/caching) explica como usar `use cache`, `cacheTag` e `cacheLife`. Esta página explica **como a revalidação funciona internamente**, para engenheiros de plataforma e usuários avançados que precisam entender o sistema para implementar [handlers de cache personalizados](/docs/app/api-reference/config/next-config-js/cacheHandlers) ou depurar o comportamento da revalidação.

## O modelo de revalidação \{#the-revalidation-model}

A maioria das rotas no Next.js pode ser revalidada sob demanda. Isso inclui rotas do App Router e rotas do Pages Router que produzem entradas de cache de ISR/prerender. Rotas do Pages Router que são otimizadas automaticamente como estáticas (saída puramente estática) não são revalidadas sob demanda. A capacidade de atualizar conteúdo em cache sem um novo deploy é parte central do [modelo de renderização](/docs/app/guides/rendering-philosophy) do Next.js.

Existem dois tipos de revalidação:

- **A revalidação baseada em tempo** usa um padrão stale-while-revalidate. O conteúdo em cache é servido imediatamente, e uma regeneração em segundo plano é disparada quando a idade do conteúdo ultrapassa a duração de [`cacheLife`](/docs/app/api-reference/functions/cacheLife) ou de `revalidate`. O conteúdo desatualizado continua sendo servido até que o conteúdo novo esteja pronto.
- **A revalidação sob demanda** invalida explicitamente o conteúdo em cache ao chamar [`revalidateTag()`](/docs/app/api-reference/functions/revalidateTag) ou [`revalidatePath()`](/docs/app/api-reference/functions/revalidatePath). A próxima requisição para esse conteúdo dispara uma nova renderização.

> **Bom saber:** as APIs de ISR sob demanda do Pages Router (por exemplo, `res.revalidate()` e o fluxo `x-prerender-revalidate`) continuam aceitas e usam o cache handler do servidor (`cacheHandler`, no singular). A opção `cacheHandlers` (no plural) é para as diretivas `'use cache'`.

## O que é revalidado \{#what-gets-revalidated}

Quando uma rota é revalidada, o Next.js regenera **tanto** a resposta HTML quanto o payload RSC (payload dos React Server Components) a partir da mesma árvore de componentes React. Os dois artefatos são armazenados juntos na mesma entrada de cache.

Essa consistência importa porque o payload RSC é usado nas navegações do lado do cliente. Navegações do navegador e navegações do lado do cliente devem mostrar o mesmo conteúdo.

### O que acontece se saírem de sincronia \{#what-happens-if-they-get-out-of-sync}

Se o cache de uma plataforma servir o HTML de uma renderização e um payload RSC de outra, os usuários podem ver conteúdo desatualizado ou divergente durante a navegação do lado do cliente. A principal mitigação é armazenar as respostas HTML e RSC juntas, com o mesmo TTL e a mesma política de invalidação, e respeitar o [header `Vary`](/docs/app/guides/cdn-caching) que o Next.js define. Veja [Cache de CDN](/docs/app/guides/cdn-caching) para detalhes.

Um problema separado, mas relacionado, é o **desalinhamento entre deploys**: durante deploys graduais (rolling), um cliente gerado pelo deploy A pode receber respostas de um servidor que roda o deploy B. O [`deploymentId`](/docs/app/api-reference/config/next-config-js/deploymentId) mitiga isso: quando o cliente detecta um ID de deploy diferente do servidor, ele dispara uma navegação completa para buscar conteúdo consistente.

## Arquitetura do sistema de tags \{#tag-system-architecture}

O Next.js usa um sistema baseado em tags para rastrear quais conteúdos em cache precisam ser invalidados. Há dois tipos de tags:

### Tags explícitas \{#explicit-tags}

Tags explícitas são definidas pelo desenvolvedor com [`cacheTag()`](/docs/app/api-reference/functions/cacheTag) dentro de uma função `use cache`, ou por meio de `next: { tags: [...] }` em uma chamada de `fetch`. Quando [`revalidateTag('my-tag', 'max')`](/docs/app/api-reference/functions/revalidateTag) é chamada, todas as entradas de cache com essa tag são invalidadas.

### Soft tags \{#soft-tags}

Soft tags são geradas automaticamente pelo Next.js com base no caminho da rota, com o prefixo `_N_T_`. Por exemplo, a rota `/blog/hello` gera soft tags como `_N_T_/layout`, `_N_T_/blog/layout`, `_N_T_/blog/hello/layout` e `_N_T_/blog/hello`. Cada segmento do caminho recebe uma tag de layout, além da própria rota final.

As soft tags permitem que o [`revalidatePath()`](/docs/app/api-reference/functions/revalidatePath) funcione pelo mesmo sistema baseado em tags. Quando `revalidatePath('/blog/hello')` é chamada, ela invalida as entradas de cache associadas à tag da rota final desse caminho e às soft tags dos layouts ancestrais (por exemplo, `_N_T_/layout`, `_N_T_/blog/layout`, `_N_T_/blog/hello/layout` e `_N_T_/blog/hello`).

Na [API de cache handlers](/docs/app/api-reference/config/next-config-js/cacheHandlers), as soft tags são passadas para o método `get()` como o parâmetro `softTags`. Seu handler deve verificar se alguma soft tag foi invalidada depois do timestamp da entrada de cache. O método `getExpiration()` retorna o timestamp de revalidação mais recente entre todas as tags fornecidas, ou `0` se nenhuma foi revalidada. Ele também pode retornar `Infinity` para sinalizar que as soft tags devem ser passadas ao `get()` e verificadas ali. Seu handler deve tratar uma entrada como desatualizada se o timestamp retornado for mais recente que o próprio timestamp da entrada. Veja a [referência da API de cache handlers](/docs/app/api-reference/config/next-config-js/cacheHandlers#getexpiration) para a semântica completa.

## Considerações sobre múltiplas instâncias \{#multi-instance-considerations}

Ao rodar várias instâncias do Next.js atrás de um load balancer, os eventos de revalidação são locais por padrão. Chamar `revalidateTag()` na instância A invalida o cache apenas nessa instância. As outras instâncias continuam servindo o conteúdo desatualizado até ficarem sabendo da invalidação.

A API de cache handlers oferece dois hooks para coordenação distribuída:

- **`updateTags()`** é chamado quando `revalidateTag()` é invocada. Seu handler deve gravar o evento de invalidação em um armazenamento compartilhado (por exemplo, Redis ou um banco de dados) para que as outras instâncias possam descobri-lo.
- **`refreshTags()`** é chamado periodicamente, mas sempre antes de iniciar uma nova requisição. Seu handler deve consultar o armazenamento compartilhado em busca de eventos de invalidação recentes e atualizar o estado local das tags de acordo.

Para detalhes de implementação e um exemplo com Redis, veja [Cache handlers personalizados](/docs/app/api-reference/config/next-config-js/cacheHandlers).

## Padrões de implementação para plataformas \{#implementation-patterns-for-platforms}

### Instância única \{#single-instance}

O cache padrão em sistema de arquivos cuida da consistência automaticamente. As gravações do cache são atômicas no sistema de arquivos local, e o estado das tags é mantido em memória. Nenhuma configuração adicional é necessária.

### Múltiplas instâncias com cache compartilhado \{#multi-instance-with-shared-cache}

Sem coordenação, cada instância serve conteúdo e trata a revalidação usando apenas o cache local. Usuários diferentes podem ver conteúdos diferentes, dependendo de qual instância atende a requisição, e a revalidação sob demanda só tem efeito na instância que recebeu a chamada.

Para reduzir essa janela e garantir que a revalidação se propague entre instâncias:

1. Armazene os timestamps de invalidação das tags em um serviço compartilhado (Redis, DynamoDB ou uma API HTTP simples).
2. Implemente `updateTags()` para gravar no serviço compartilhado.
3. Implemente `refreshTags()` para ler do serviço compartilhado. Seu handler precisa capturar erros em `refreshTags()`: se a função lançar uma exceção, o erro se propaga como falha da requisição. Capturar o erro permite que as requisições continuem com o último estado local conhecido das tags, servindo conteúdo potencialmente desatualizado até que a conectividade seja restabelecida.
4. Armazene as entradas de cache (HTML + payload RSC) em armazenamento compartilhado. Gravações atômicas reduzem ainda mais a janela de divergência, mas não são necessárias para a corretude.

### Integração com CDN \{#cdn-integration}

Se um CDN armazena em cache as respostas do Next.js, ele deve respeitar o header `Vary` e as diretivas de `Cache-Control` que o Next.js define. Não armazene as respostas de HTML e de payload RSC separadamente, com TTLs diferentes. Veja [Cache de CDN](/docs/app/guides/cdn-caching) para detalhes.

## Degradação graciosa \{#graceful-degradation}

O sistema de revalidação prioriza disponibilidade em vez de consistência estrita. O conteúdo é sempre servido, mesmo quando as garantias da infraestrutura não podem ser totalmente cumpridas:

- **Falha de gravação no cache**: a resposta ainda é servida ao usuário, porque as gravações são assíncronas. A entrada de cache se perde, e a próxima requisição dispara uma nova renderização.
- **Falha de leitura no cache**: seu handler deve capturar erros internos e retornar `undefined` (o sinal de cache miss). A rota é então renderizada no servidor do zero. Um erro lançado não é tratado como cache miss; ele se propaga como erro de renderização, então sempre retorne `undefined` para sinalizar um miss.
- **Inconsistência entre HTML e RSC**: se um CDN armazena HTML e RSC com TTLs ou momentos de invalidação diferentes, os usuários podem ver conteúdos divergentes durante a navegação do lado do cliente. Armazene-os juntos e respeite o `Vary` para evitar isso.
- **Desalinhamento entre deploys**: durante deploys graduais, configure o [`deploymentId`](/docs/app/api-reference/config/next-config-js/deploymentId) para que uma mudança no build ID dispare uma navegação completa e busque conteúdo consistente.

Falhas de cache resultam em desempenho degradado (conteúdo desatualizado, renderizações extras), e não em apps quebrados.
