O Next.js define headers padrão de `Cache-Control` que os CDNs podem usar para armazenar as respostas na borda. Esta página aborda o que funciona hoje, onde o cache de CDN é um desafio e a direção para eliminar a dependência de headers personalizados.

## O que funciona hoje \{#what-works-today}

### Headers Cache-Control \{#cache-control-headers}

O Next.js define headers `Cache-Control` com base na estratégia de renderização de cada rota:

- **Páginas estáticas** (sem revalidação): `s-maxage=31536000` (um ano)
- **Páginas ISR** (revalidação baseada em tempo): `s-maxage={revalidate}, stale-while-revalidate={expire - revalidate}`. O `expire` padrão é de um ano, então o `stale-while-revalidate` já vem incluído no header da resposta por padrão. Você pode personalizar isso com [`cacheLife`](/docs/app/api-reference/functions/cacheLife).
- **Páginas dinâmicas** (sem cache): `private, no-cache, no-store, max-age=0, must-revalidate`

CDNs que respeitam `s-maxage` e `stale-while-revalidate` podem armazenar em cache páginas estáticas e ISR na borda. No entanto, só o cache no CDN não cobre a revalidação sob demanda ([`revalidateTag()`](/docs/app/api-reference/functions/revalidateTag) / [`revalidatePath()`](/docs/app/api-reference/functions/revalidatePath)): essas chamadas invalidam o cache do servidor do Next.js, mas o CDN continua servindo a cópia dele até o TTL de `s-maxage` expirar. Para propagar a revalidação sob demanda ao CDN, dispare purges no CDN junto com a chamada de revalidação. Um padrão comum é: chamar `revalidateTag()`/`revalidatePath()` para invalidar o cache do servidor do Next.js e, em seguida, chamar a API de purge do CDN para as chaves afetadas (incluindo as variantes de HTML e de RSC).

### Arquivos estáticos \{#static-assets}

Arquivos estáticos (JavaScript, CSS, imagens, fontes) servidos a partir de `/_next/static/` incluem hashes de conteúdo nos nomes dos arquivos e têm `max-age` de 1 ano e a diretiva `immutable`: `public, max-age=31536000, immutable`

Você pode usar o [`assetPrefix`](/docs/app/api-reference/config/next-config-js/assetPrefix) para servir arquivos estáticos a partir de outro domínio ou de outra origem de CDN.

### Prefetches estáticos (rotas com PPR ativado) \{#static-prefetches-ppr-enabled-routes}

Quando uma rota tem Partial Prerendering ativado e o header `next-router-prefetch` está definido (indicando um prefetch estático), a resposta é determinística: ela retorna o mesmo conteúdo pré-renderizado, independentemente do estado do roteador do cliente. O header `next-router-state-tree` não é analisado nessas requisições, então não afeta a resposta.

Para rotas com PPR ativado, um CDN pode armazenar em cache as respostas de prefetch estático se ele:

1. Incluir o parâmetro de busca `_rsc` na chave de cache (para distinguir as variantes de prefetch das respostas HTML).
2. Respeitar os headers `Cache-Control` que o Next.js define na resposta.

> **Bom saber:** para rotas sem PPR, o header `next-router-state-tree` é lido nas requisições de prefetch para determinar quais segmentos incluir, o que aumenta a variação do cache (`vary`), já que o header carrega o estado atual do roteador. Quando o Cache Components está ativado, os prefetches por segmento já usam rotas baseadas em pathname (por exemplo, `/page.segments/_tree.segment.rsc`), e os CDNs podem armazenar essas rotas com chaves de cache padrão baseadas em pathname.

## Onde o cache de CDN é um desafio \{#where-cdn-caching-is-challenging}

Respostas do App Router podem variar com base em vários headers personalizados da requisição. O Next.js define um header `Vary` nas respostas para sinalizar isso aos CDNs:

- `rsc`: se a requisição deve retornar um payload de React Server Components (RSC) em vez de HTML
- `next-router-state-tree`: o estado atual do roteador do cliente, usado para atualizações de segmentos específicos durante navegações dinâmicas
- `next-router-prefetch`: se esta é uma requisição de prefetch
- `next-router-segment-prefetch`: o segmento específico alvo do prefetch
- `next-url`: adicionado apenas para rotas que usam [rotas de interceptação](/docs/app/api-reference/file-conventions/intercepting-routes), carrega a URL interceptada

> **Bom saber:** [`proxy.js`](/docs/app/api-reference/file-conventions/proxy) (anteriormente Middleware) deve rodar antes do cache de CDN, para continuar sendo a fonte da verdade para autenticação, redirecionamentos e rewrites. Se seu deployment coloca o `proxy.js` atrás do CDN, configure a camada de cache para não armazenar em cache as rotas que dependem das decisões do `proxy.js`.

Muitos CDNs não funcionam com `Vary` sem configuração adicional. O Next.js resolve isso com o parâmetro de busca `_rsc`: um hash dos valores relevantes dos headers da requisição, que funciona como chave de cache e garante que variantes diferentes de resposta recebam chaves de cache diferentes. Isso garante respostas corretas mesmo em CDNs que ignoram `Vary`.

## Como tratar headers no CDN \{#handling-headers-at-the-cdn}

### O que você pode ignorar com segurança \{#what-you-can-safely-ignore}

Estes headers podem ser omitidos em casos específicos sem causar erros de protocolo. O servidor ainda retorna uma resposta interpretável, mas ela pode ser maior ou menos direcionada à navegação específica:

**`next-router-state-tree`**: quando omitido em requisições RSC que não são de prefetch, o servidor retorna um payload completo em vez de uma atualização direcionada de segmento.

**`next-router-segment-prefetch`**: quando omitido em requisições de prefetch, o servidor usa um payload de prefetch mais amplo em vez de um específico por segmento.

**`next-url`**: usado nas [rotas de interceptação](/docs/app/api-reference/file-conventions/intercepting-routes) para variar a resposta conforme a página de origem. Se omitido, as rotas de interceptação não funcionam, pois o servidor não sabe qual caminho original usar para fazer a correspondência. Com `next-url` omitido, a resposta retornada é a de navegação comum: o usuário vê a página de destino em vez da página de destino interceptada.

### O que você deve preservar \{#what-you-must-preserve}

**O header `rsc`** precisa ser encaminhado do cliente para o servidor. Esse header diz ao servidor para retornar um payload RSC em vez de HTML. Se um CDN o remover, o servidor retorna HTML quando o roteador do lado do cliente espera dados RSC, o que quebra a navegação do lado do cliente e causa navegações completas do navegador no lugar. O header `Vary` e o parâmetro `_rsc` existem justamente para impedir que os CDNs sirvam uma resposta HTML em cache para uma requisição RSC (ou o contrário).

**Quando `next-router-prefetch` estiver presente, preserve tanto o header de prefetch quanto o parâmetro de busca `_rsc`.** Para fluxos de prefetch, `_rsc` é um discriminador obrigatório de cache-busting e deve ser tratado como obrigatório.

**O parâmetro de busca `_rsc`** precisa estar na chave de cache. Ele distingue as variantes de resposta (HTML e RSC, diferentes tipos de prefetch). Garanta que seu CDN não remova parâmetros de busca das chaves de cache, o que alguns CDNs fazem por padrão. Por padrão, quando uma requisição RSC chega sem o valor correto de `_rsc`, o servidor responde com um **redirecionamento 307** para a URL com o hash correto. Esse comportamento pode ser desativado definindo `experimental.validateRSCRequestHeaders` como `false`. Os CDNs devem seguir esse redirecionamento. Plataformas que calculam o hash na origem podem reescrever as requisições para incluir o `_rsc` correto antes de encaminhá-las, evitando uma ida e volta extra.

> **Bom saber:** hoje, `next-url` é incluído no hash de `_rsc` mesmo durante prefetches estáticos. Isso significa que você não pode ignorá-lo com segurança no esquema atual sem correr o risco de cache misses. A direção baseada em pathname descrita abaixo resolve essa lacuna.

## Direção: chave de cache baseada em pathname \{#direction-pathname-based-cache-keying}

A equipe do Next.js está trabalhando para mover todas as entradas que afetam o cache para o pathname da URL, eliminando a necessidade de `Vary` em headers personalizados e removendo o parâmetro de busca `_rsc`. Isso resolve os desafios de cache de CDN descritos acima.

### Como funciona \{#how-it-works}

A abordagem estende o esquema de roteamento que o [`output: 'export'`](/docs/app/guides/static-exports) e os prefetches por segmento já usam hoje. Extensões de arquivo no pathname identificam o tipo de resposta:

- **RSC da página inteira**: `/my/page.rsc` retorna o payload RSC da página inteira
- **RSC por segmento**: `/my/page.segments/path/to/segment.segment.rsc` retorna o payload RSC de um segmento específico

Nesse modelo:

- **O pathname determina a chave de cache.** Qualquer coisa no pathname afeta qual variante de resposta é retornada.
- **Parâmetros de busca podem ser descartados com segurança**, sem afetar as respostas retornadas.
- **Headers padrão de cache HTTP** (`Cache-Control`, `max-age` etc.) são respeitados normalmente.
- **Não é preciso suporte a `Vary`** no CDN.

Um CDN armazenaria as respostas do Next.js usando o pathname como chave de cache, ignorando parâmetros de busca e respeitando os headers padrão de `Cache-Control`. Não há necessidade de entender `Vary`, inspecionar headers personalizados ou programar lógica na borda.

### O que muda para as rotas de interceptação \{#what-changes-for-interception-routes}

No esquema atual, `next-url` contribui para o hash de `_rsc`, então descartá-lo causa cache misses. No esquema baseado em pathname, a variabilidade da interceptação seria codificada em um parâmetro de busca (e não no pathname):

- Se o CDN preservar os parâmetros de busca, a interceptação funciona corretamente.
- Se o CDN descartar os parâmetros de busca, a interceptação não funciona. Ela voltaria para a página não interceptada sem erro, e as navegações do lado do cliente não quebram.

Isso torna o suporte a rotas de interceptação uma capacidade opcional do CDN, e não um requisito.

### Status atual \{#current-status}

Essa direção estende padrões que já estão operacionais no código (caminhos de prefetch por segmento, modo `output: 'export'`). Ela está em desenvolvimento ativo.
