Uma **Server Action** é uma [React Server Function](https://react.dev/reference/rsc/server-functions) invocada pelos mecanismos de action do React, como `<form action>`, `<button formAction>` ou uma transição no cliente.

Você cria uma adicionando a diretiva [`'use server'`](/docs/app/api-reference/directives/use-server) e, em seguida, a invoca a partir de um formulário, de um event handler ou de um `useEffect` envolvido em `startTransition`. Para o básico sobre como criar e invocar Server Functions, veja [Mutando dados](/docs/app/getting-started/mutating-data) e o [guia de Forms](/docs/app/guides/forms).

Esta página trata das partes das Server Actions que são específicas do Next.js: como elas costumam se mapear para mutações, como a resposta carrega tanto os dados retornados quanto a UI renderizada novamente, como o cliente as despacha, a fronteira de segurança que o framework impõe e a configuração disponível.

## Despacho sequencial no cliente \{#sequential-dispatch-on-the-client}

O Next.js despacha as Server Actions uma por vez para cada cliente. Se um usuário disparar três actions em sequência rápida, a segunda espera a primeira terminar, e a terceira espera a segunda. Isso mantém a árvore do servidor renderizada novamente consistente com o resultado da action que a produziu.

Uma consequência: não confie no `Promise.all` para paralelizar Server Actions a partir do cliente. Se você precisa de trabalho em paralelo, faça isso dentro de uma única Server Action, busque dados em paralelo a partir de um [Server Component](/docs/app/getting-started/fetching-data#server-components) ou use um [Route Handler](/docs/app/guides/backend-for-frontend#manipulating-data) para requisições que não são mutações.

> **Bom saber:** Isso é uma propriedade do despachante do cliente, não das Server Functions em geral. O servidor não enfileira Server Actions. Cada uma roda na própria requisição assim que chega e pode fazer tudo o que uma função assíncrona pode fazer.

## Uma única resposta carrega dados e UI \{#a-single-response-carries-data-and-ui}

Quando uma Server Action dispara uma revalidação imediata, o Next.js faz o trabalho dentro de uma única requisição HTTP: executa a action e, em seguida, renderiza novamente a rota atual no servidor. A resposta que volta contém as duas partes no mesmo stream do Flight:

- O valor retornado pela action, consumido pelo `useActionState` ou pela promise aguardada no cliente.
- Um [RSC Payload](/docs/app/glossary#rsc-payload) recém-renderizado para a rota atual, que o cliente aplica como uma navegação já preenchida.

O código da sua aplicação não precisa de uma busca adicional para ver a UI atualizada da página atual.

Uma nova renderização entra na mesma resposta quando a action faz qualquer uma destas coisas:

- Chama [`updateTag`](/docs/app/api-reference/functions/updateTag) ou [`revalidatePath`](/docs/app/api-reference/functions/revalidatePath) para invalidar imediatamente os dados em cache.
- Chama [`revalidateTag`](/docs/app/api-reference/functions/revalidateTag#client-cache-behavior) com um perfil que resulta em `expire: 0`, incluindo `{ expire: 0 }`.
- Chama [`refresh`](/docs/app/api-reference/functions/refresh) para buscar novamente o RSC Payload da rota atual.
- Altera cookies por meio de [`cookies()`](/docs/app/api-reference/functions/cookies#understanding-cookie-behavior-in-server-functions). Definir ou excluir um cookie renderiza novamente a página atual automaticamente, para que a UI reflita o novo valor.
- Chama [`redirect`](/docs/app/api-reference/functions/redirect). A resposta navega o router e envia em stream o RSC Payload do destino.

```ts filename="app/posts/actions.ts"
'use server'

import { revalidatePath } from 'next/cache'
import { auth } from '@/lib/auth'
import { db } from '@/lib/db'

export async function createPost(formData: FormData) {
  const session = await auth()
  if (!session?.user) throw new Error('Unauthorized')

  await db.post.create({
    data: {
      title: String(formData.get('title')),
      authorId: session.user.id,
    },
  })

  revalidatePath('/posts')
}
```

A mutação, a invalidação do cache e a renderização da página acontecem todas em uma única ida e volta. Como o [`redirect`](/docs/app/api-reference/functions/redirect#behavior) lança uma exceção de controle de fluxo, qualquer código depois dele não é executado. Coloque as chamadas de revalidação antes do `redirect` se o destino precisar dos dados atualizados.

O [`revalidateTag`](/docs/app/api-reference/functions/revalidateTag) com um perfil de stale-while-revalidate é a exceção: ele marca a tag para atualização em segundo plano e **não** inclui uma nova renderização na resposta da action. A página reflete a mudança em uma leitura posterior. Uma action que não faz nada disso traz apenas o valor retornado, e a rota atual não é renderizada novamente.

## Segurança \{#security}

Uma Server Action roda como uma requisição POST para a página que a invoca. Em tempo de build, a diretiva `'use server'` faz o compilador trocar a implementação da função, nos bundles do cliente, por uma referência (um ID de action mais um despachante) que faz POST de volta para o servidor. A implementação continua no servidor, mas a rota é acessível a qualquer pessoa que consiga enviar o mesmo POST. Trate toda action como um ponto de entrada não confiável.

O Next.js aplica algumas proteções no nível do framework:

- **Verificação de CSRF.** O `Origin` da requisição é comparado ao `Host` (ou ao `X-Forwarded-Host`). Requisições divergentes são rejeitadas. Configure [`experimental.serverActions.allowedOrigins`](/docs/app/api-reference/config/next-config-js/serverActions#allowedorigins) para domínios de proxy ou CDN.
- **Limite de tamanho do body.** Requisições de action são limitadas a 1MB por padrão. Configure [`experimental.serverActions.bodySizeLimit`](/docs/app/api-reference/config/next-config-js/serverActions#bodysizelimit) quando precisar aceitar payloads maiores.
- **IDs de action criptografados e eliminação de código morto.** As referências de action são criptografadas em tempo de build, e Server Functions não utilizadas são removidas dos bundles do cliente, para que não tenham um endpoint público. Veja [recursos de segurança integrados das Server Actions](/docs/app/guides/data-security#built-in-server-actions-security-features).
- **Criptografia de variáveis de closure.** As variáveis capturadas por uma action inline são criptografadas antes de serem enviadas ao cliente. Em deployments com várias instâncias ou self-hosted, defina `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` com uma chave estável compartilhada entre as instâncias. Veja [Closures e criptografia](/docs/app/guides/data-security#closures-and-encryption).

As proteções do framework não substituem as verificações no nível da aplicação. Dentro de cada action:

- **Autentique e autorize.** Bloquear a renderização no momento da renderização (exibir um formulário só em uma página autenticada) não é uma fronteira de segurança, porque requisições podem ser enviadas sem passar pela UI.
- **Valide as entradas.** Trate `FormData`, parâmetros de query e headers como não confiáveis.
- **Limite os valores retornados.** Os retornos da action são serializados para o cliente. Modele-os para o que a UI renderiza, e não registros brutos do banco de dados.

Para padrões completos, incluindo uma Data Access Layer, tainting de valores retornados e limitação de taxa, veja o [guia de Segurança de dados](/docs/app/guides/data-security#mutating-data).

Operações destrutivas, como exclusões, podem exigir um tratamento mais rigoroso, como verificações de sessão elevadas ou nova autenticação, e uma falha explícita quando essas verificações não passam.

```ts filename="app/posts/actions.ts" highlight={6,7,8}
'use server'

import { auth } from '@/lib/auth'

export async function deletePost(postId: string) {
  const session = await auth()
  if (!session?.user) throw new Error('Unauthorized')
  if (!(await canDelete(session.user, postId))) throw new Error('Forbidden')

  await db.post.delete({ where: { id: postId } })
}
```

Se você ativou a flag experimental [`authInterrupts`](/docs/app/api-reference/config/next-config-js/authInterrupts), pode lançar [`unauthorized()`](/docs/app/api-reference/functions/unauthorized) e [`forbidden()`](/docs/app/api-reference/functions/forbidden), de `next/navigation`, no lugar. Assim, o Next.js renderiza automaticamente o segmento de UI `unauthorized.tsx` / `forbidden.tsx` correspondente.

Por exemplo, um cliente diz legitimamente ao servidor _qual_ item deve ser alterado, mas não deve fornecer o conteúdo da linha nem a sua propriedade. Envie uma referência (normalmente um ID) mais a alteração do usuário, e releia o restante a partir de uma fonte confiável, usando a sessão. A validação de schema (zod ou similar) só verifica a _forma_ da entrada. Um objeto `Item` bem formado ainda pode se referir a uma linha que o chamador não possui.

```ts filename="app/items/actions.ts"
'use server'

import { auth } from '@/lib/auth'
import { db } from '@/lib/db'

// Unsafe: no auth, no ownership check. The whole item, including its id, comes
// from the client, so anyone who can POST here can mark any item complete.
export async function completeItemUnsafe(item: Item) {
  await db.item.update({ where: { id: item.id }, data: { completed: true } })
}

// Safe: take only the change, derive identity from the session, look up by ownership.
export async function completeItem(itemId: string) {
  const session = await auth()
  if (!session?.user) return

  const item = await db.item.findFirst({
    where: { id: itemId, ownerId: session.user.id },
  })
  if (!item) return

  await db.item.update({ where: { id: item.id }, data: { completed: true } })
}
```

## Escolhendo uma atualização de cache \{#choosing-a-cache-update}

Depois de mutar dados, a revalidação sob demanda atualiza o cache do servidor, o router do cliente ou ambos. Escolha de acordo com o que precisa mudar:

- [`updateTag`](/docs/app/api-reference/functions/updateTag): expiração imediata de uma tag. A próxima leitura (incluindo a renderização da rota que acompanha a resposta da action) espera pelos dados novos. Use quando a action precisa de **read-your-own-writes**, para que o usuário veja a sua mudança imediatamente. Somente Server Actions.
- [`revalidateTag`](/docs/app/api-reference/functions/revalidateTag): atualização stale-while-revalidate de uma tag com um perfil de cache-life, como `'max'`. As leituras seguintes recebem o valor antigo enquanto uma nova busca acontece em segundo plano. A chamada **não** dispara uma nova renderização imediata. Veja o [comportamento do cache no cliente](/docs/app/api-reference/functions/updateTag#client-cache-behavior) para perfis de expiração imediata.
- [`revalidatePath`](/docs/app/api-reference/functions/revalidatePath): invalida por caminho de URL. Use quando uma única rota é afetada e usar tags seria exagero.
- [`refresh`](/docs/app/api-reference/functions/refresh): busca novamente o RSC Payload da rota atual sem invalidar os dados em cache. Use quando a view depende de um estado fora do cache que a action acabou de alterar.

Quando `updateTag`, `revalidatePath` ou `refresh` é executado, o Next.js renderiza novamente a rota atual no servidor e inclui um [RSC Payload](/docs/app/glossary#rsc-payload) recém-renderizado na resposta da action, para que a página reflita a mudança na mesma ida e volta. O `revalidateTag` com um perfil de stale-while-revalidate intencionalmente pula essa nova renderização imediata.

Diferente do [`redirect`](/docs/app/api-reference/functions/redirect), nenhuma dessas funções lança exceção. Assim, uma action pode chamá-las e ainda retornar um valor para quem a chamou. Veja [Como funciona a revalidação](/docs/app/guides/how-revalidation-works) para entender o modelo por trás disso.

## Configuração \{#configuration}

A opção [`experimental.serverActions`](/docs/app/api-reference/config/next-config-js/serverActions) no `next.config.js` controla o comportamento no nível do framework:

```js filename="next.config.js"
/** @type {import('next').NextConfig} */
module.exports = {
  experimental: {
    serverActions: {
      allowedOrigins: ['my-proxy.com', '*.my-proxy.com'],
      bodySizeLimit: '2mb',
    },
  },
}
```

> **Bom saber**: As Server Actions são estáveis e vêm habilitadas por padrão no Next.js 14 e versões posteriores. A API de configuração em `experimental.serverActions` continua experimental.

Para a chave de criptografia das closures, defina `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` no ambiente de deploy. Veja [Self-hosting: chave de criptografia das Server Functions](/docs/app/guides/self-hosting#server-functions-encryption-key) para orientações específicas de deploy.

## Considerações de deploy \{#deployment-considerations}

Cada Server Action é identificada pelo [ID da action](#security) que faz parte dos seus artefatos de build. Novos deployments normalmente geram novos IDs (o Next.js os rotaciona no máximo a cada 14 dias, mesmo quando o código-fonte não muda), então um cliente que ainda roda o build anterior pode invocar um ID de action que não existe mais. O erro aparece como "[Failed to find Server Action](https://nextjs.org/docs/messages/failed-to-find-server-action)".

Para minimizar os impactos:

- Prefira deployments graduais (rolling) a trocas abruptas, quando for provável que usuários ativos estejam no meio de uma mutação.
- Mantenha `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` estável entre as instâncias, para que as referências de action continuem descriptografáveis em todas elas.
- Mostre o erro na UI como um caminho de nova tentativa, em vez de uma falha definitiva, para que um refresh recupere o usuário.
