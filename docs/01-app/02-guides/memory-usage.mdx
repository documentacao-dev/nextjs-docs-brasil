À medida que os apps crescem e ganham mais recursos, eles podem exigir mais recursos ao rodar localmente ou ao gerar builds de produção.

Vamos explorar algumas estratégias e técnicas para otimizar a memória e resolver problemas comuns de memória no Next.js.

## Reduzir o número de dependências \{#reduce-number-of-dependencies}

Apps com muitas dependências usam mais memória.

O [Bundle Analyzer](/docs/app/guides/package-bundling) pode ajudar você a investigar grandes dependências do seu app que talvez possam ser removidas para melhorar a performance e o uso de memória.

## Teste o `experimental.webpackMemoryOptimizations` \{#try-experimentalwebpackmemoryoptimizations}

A partir da `v15.0.0`, você pode adicionar `experimental.webpackMemoryOptimizations: true` ao seu arquivo `next.config.js` para alterar o comportamento do webpack, reduzindo o uso máximo de memória ao custo de um pequeno aumento no tempo de compilação.

> **Bom saber**: Este recurso ainda é experimental, para ser testado em mais projetos antes, mas é considerado de baixo risco.

## Execute `next build` com `--experimental-debug-memory-usage` \{#run-next-build-with---experimental-debug-memory-usage}

A partir da `14.2.0`, você pode executar `next build --experimental-debug-memory-usage` para rodar o build em um modo em que o Next.js imprime continuamente informações sobre o uso de memória durante todo o build, como o uso do heap e estatísticas do garbage collection. Snapshots do heap também são gerados automaticamente quando o uso de memória se aproxima do limite configurado.

> **Bom saber**: Este recurso não é compatível com a opção de worker de build do webpack, que é habilitada automaticamente, a menos que você tenha uma configuração personalizada do webpack.

## Gravar um heap profile \{#record-a-heap-profile}

Para procurar problemas de memória, você pode gravar um heap profile do Node.js e carregá-lo no Chrome DevTools para identificar possíveis origens de vazamentos de memória.

No seu terminal, passe a flag `--heap-prof` para o Node.js ao iniciar o build do seu app Next.js:

```sh
node --heap-prof node_modules/next/dist/bin/next build
```

Ao final do build, o Node.js vai criar um arquivo `.heapprofile`.

No Chrome DevTools, você pode abrir a aba Memory e clicar no botão "Load Profile" para visualizar o arquivo.

## Analisar um snapshot do heap \{#analyze-a-snapshot-of-the-heap}

Você pode usar uma ferramenta de inspeção para analisar o uso de memória do app.

Ao executar o comando `next build` ou `next dev`, adicione `NODE_OPTIONS=--inspect` no início do comando. Isso vai expor o agente de inspeção na porta padrão.
Se você quiser pausar antes de qualquer código do usuário começar, pode passar `--inspect-brk`. Enquanto o processo está em execução, você pode usar uma ferramenta como o Chrome DevTools para se conectar à porta de depuração, gravar e analisar um snapshot do heap e ver qual memória está sendo retida.

A partir da `14.2.0`, você também pode executar `next build` com a flag `--experimental-debug-memory-usage`, para facilitar a geração de snapshots do heap.

Nesse modo, você pode enviar um sinal `SIGUSR2` ao processo a qualquer momento, e o processo vai gerar um snapshot do heap.

O snapshot do heap será salvo na raiz do projeto Next.js e pode ser carregado em qualquer analisador de heap, como o Chrome DevTools, para ver o que está sendo retido. Este modo ainda não é compatível com os workers de build do webpack.

Veja [como gravar e analisar snapshots do heap](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots) para mais informações.

## Worker de build do webpack \{#webpack-build-worker}

O worker de build do webpack permite executar as compilações do webpack em um worker separado do Node.js, o que reduz o uso de memória do seu app durante os builds.

A partir da `v14.1.0`, esta opção vem habilitada por padrão, desde que o seu app não tenha uma configuração personalizada do webpack.

Se você estiver usando uma versão mais antiga do Next.js ou tiver uma configuração personalizada do webpack, pode habilitar esta opção definindo `experimental.webpackBuildWorker: true` dentro do seu `next.config.js`.

> **Bom saber**: Este recurso pode não ser compatível com todos os plugins personalizados do webpack.

## Desativar o cache do webpack \{#disable-webpack-cache}

O [cache do webpack](https://webpack.js.org/configuration/cache/) salva os módulos gerados pelo webpack na memória e/ou em disco para melhorar a velocidade dos builds. Isso pode ajudar na performance, mas também aumenta o uso de memória do seu app para armazenar os dados em cache.

Você pode desativar esse comportamento adicionando uma [configuração personalizada do webpack](/docs/app/api-reference/config/next-config-js/webpack) ao seu app:

```js filename="next.config.mjs"
/** @type {import('next').NextConfig} */
const nextConfig = {
  webpack: (
    config,
    { buildId, dev, isServer, defaultLoaders, nextRuntime, webpack }
  ) => {
    if (config.cache && !dev) {
      config.cache = Object.freeze({
        type: 'memory',
      })
    }
    // Important: return the modified config
    return config
  },
}

export default nextConfig
```

## Desativar a análise estática \{#disable-static-analysis}

A verificação de tipos pode exigir muita memória, especialmente em projetos grandes.
No entanto, a maioria dos projetos tem um runner de CI dedicado que já cuida dessas tarefas.
Quando o build apresenta problemas de falta de memória (out-of-memory) na etapa "Running TypeScript", você pode desativar essa tarefa durante os builds:

```js filename="next.config.mjs"
/** @type {import('next').NextConfig} */
const nextConfig = {
  typescript: {
    // !! WARN !!
    // Dangerously allow production builds to successfully complete even if
    // your project has type errors.
    // !! WARN !!
    ignoreBuildErrors: true,
  },
}

export default nextConfig
```

- [Ignorando erros do TypeScript](/docs/app/api-reference/config/typescript#disabling-typescript-errors-in-production)

Tenha em mente que isso pode gerar deploys com defeito por causa de erros de tipo.
Recomendamos fortemente promover builds para produção somente depois que a análise estática for concluída.
Se você faz deploy na Vercel, pode conferir o [guia de deployments de staging](https://vercel.com/docs/deployments/managing-deployments#staging-and-promoting-a-production-deployment) para aprender a promover builds para produção depois que as tarefas personalizadas forem concluídas com sucesso.

## Desativar source maps \{#disable-source-maps}

Gerar source maps consome memória extra durante o processo de build.

Você pode desativar a geração de source maps adicionando `productionBrowserSourceMaps: false` e `experimental.serverSourceMaps: false` à configuração do seu Next.js.

O Next.js usa source maps por padrão durante a fase de prerendering do `next build`.
Se você encontrar problemas de memória de forma consistente nessa fase (depois de "Generating static pages"),
pode tentar desativar os source maps nessa fase adicionando `enablePrerenderSourceMaps: false` à configuração do seu Next.js.

> **Bom saber**: Alguns plugins podem ativar source maps e podem precisar de configuração personalizada para serem desativados.

## Problemas de memória no Edge \{#edge-memory-issues}

O Next.js `v14.1.3` corrigiu um problema de memória ao usar o Edge Runtime. Atualize para essa versão (ou uma posterior) para verificar se ela resolve o seu problema.

## Pré-carregamento de entradas \{#preloading-entries}

Quando o servidor do Next.js inicia, ele pré-carrega na memória os módulos JavaScript de cada página, em vez de fazer isso no momento da requisição.

Essa otimização permite tempos de resposta mais rápidos, em troca de um consumo de memória inicial maior.

Para desativar essa otimização, defina a flag `experimental.preloadEntriesOnStart` como `false`.

```ts filename="next.config.ts" switcher
import type { NextConfig } from 'next'

const config: NextConfig = {
  experimental: {
    preloadEntriesOnStart: false,
  },
}

export default config
```

```js filename="next.config.mjs" switcher
/** @type {import('next').NextConfig} */
const config = {
  experimental: {
    preloadEntriesOnStart: false,
  },
}

export default config
```

O Next.js não descarrega esses módulos JavaScript da memória, o que significa que, mesmo com essa otimização desativada, o consumo de memória do seu servidor Next.js vai acabar sendo o mesmo se todas as páginas forem acessadas em algum momento.
