Partial Prerendering (PPR) combina renderização estática e dinâmica em uma única rota. No build, o Next.js gera uma casca HTML estática e um blob `postponedState` para cada rota com PPR ativado. Na requisição, a casca é servida imediatamente, e as partes dinâmicas são renderizadas e enviadas por streaming ao cliente.

Esta página explica como as plataformas podem implementar suporte a PPR em diferentes níveis de sofisticação.

## Como o PPR funciona \{#how-ppr-works}

### No build \{#build-time}

Para cada rota com PPR, o Next.js produz:

- Uma **casca HTML estática** contendo todo o conteúdo que pode passar por prerendering, com fallbacks de [Suspense](/docs/app/guides/streaming#what-is-streaming) nos pontos onde o conteúdo dinâmico vai aparecer.
- Um valor **`postponedState`**: uma string serializada. Trate-o como opaco: repasse sem analisar nem modificar. Alterar o `postponedState` produz uma saída de renderização dinâmica incorreta.
- Um **payload RSC** para as partes estáticas da página.

### Na requisição \{#request-time}

Quando uma requisição chega a uma rota com PPR:

1. O servidor envia a casca HTML estática ao cliente imediatamente.
2. O servidor retoma a renderização das partes dinâmicas usando o estado adiado.
3. O conteúdo dinâmico é enviado por streaming ao cliente, permitindo que o React faça a hydration dos limites de Suspense adiados.

O cliente vê a casca estática instantaneamente, e depois o conteúdo dinâmico aparece conforme é resolvido.

## Armazenando os artefatos do PPR \{#storing-ppr-artifacts}

Cada rota com PPR exige que dois artefatos sejam armazenados juntos:

1. A casca HTML estática.
2. O blob `postponedState`.

Eles devem ser armazenados e atualizados de forma atômica. Quando uma rota com PPR é revalidada (por [revalidação baseada em tempo](/docs/app/guides/incremental-static-regeneration) ou por [revalidação sob demanda](/docs/app/api-reference/functions/revalidateTag)), o Next.js regenera a casca e o estado adiado juntos. Servir uma casca nova com um `postponedState` antigo, ou o contrário, vai produzir conteúdo dinâmico incorreto.

Use [`requestMeta.onCacheEntryV2`](/docs/app/api-reference/adapters/implementing-ppr-in-an-adapter) no seu adapter para observar as atualizações de cache e propagá-las para o seu backend de armazenamento.

## Implementação somente com origem \{#origin-only-implementation}

**Esta é a abordagem mais simples e funciona em qualquer plataforma que ofereça respostas HTTP em streaming.**

Todas as requisições vão diretamente para o servidor Next.js. O servidor lê a casca do cache local, envia, e depois renderiza e envia por streaming o conteúdo dinâmico. É o que o `next start` faz por padrão.

Nenhuma infraestrutura adicional é necessária. Se sua plataforma oferece respostas HTTP em streaming, ela oferece suporte a PPR.

## Casca no CDN + computação na origem \{#cdn-shell--origin-compute}

Para um TTFB melhor, a casca HTML estática pode ser armazenada em cache na borda do CDN. Quando uma requisição chega:

1. O CDN serve a casca em cache imediatamente (latência de borda).
2. O CDN envia uma requisição de retomada ao servidor de origem (idealmente em paralelo com o envio da casca em streaming).
3. O servidor de origem renderiza apenas as partes dinâmicas e as envia de volta por streaming.
4. O CDN concatena a casca e o conteúdo dinâmico em uma única resposta em streaming para o cliente.

Isso exige que o CDN ofereça um mecanismo para combinar conteúdo em cache e conteúdo dinâmico em uma única resposta em streaming. O TTFB da casca estática cai para a latência de borda, enquanto o conteúdo dinâmico continua vindo por streaming da origem.

Para a menor latência possível, a casca pode ser servida a partir de armazenamento na borda (por exemplo, um KV store preenchido durante o `onBuildComplete`) em vez de um cache de CDN. Essa é uma decisão de arquitetura da plataforma e não exige nenhuma mudança no app Next.js.

## O protocolo de retomada \{#the-resume-protocol}

O **protocolo de retomada** instrui o handler do Next.js a pular a casca e renderizar apenas as partes dinâmicas. Ele é usado por arquiteturas de CDN para origem e por deployments baseados em adapter que servem a casca separadamente.

No `next start` padrão, o servidor cuida da casca e da renderização dinâmica em uma única passada, automaticamente.

### CDN para origem \{#cdn-to-origin}

Quando o CDN faz uma requisição HTTP para uma origem Next.js separada:

- Envie uma requisição **POST** para a rota com o header `next-resume: 1`.
- Inclua o blob `postponedState` como o **corpo da requisição**.
- O servidor vai renderizar apenas os limites de Suspense adiados e enviar o resultado por streaming.

> **Bom saber:** quando uma requisição POST combina uma Server Action com a retomada do PPR, o corpo da requisição contém o estado adiado seguido do corpo da action. O header `x-next-resume-state-length` carrega o tamanho em bytes do prefixo do estado adiado, para que o handler possa separar os dois. Para uma retomada de PPR pura (o caso comum), o corpo inteiro da requisição é o estado adiado, e esse header não é necessário.

### Baseado em adapter \{#adapter-based}

Quando a plataforma invoca a função handler diretamente:

- Chame o handler de entrada com `req.method` definido como `'POST'`, o header `next-resume: 1` na requisição e o `postponedState` como corpo da requisição. (Você também pode passar `requestMeta: { postponed: postponedState }` como terceiro argumento na invocação do handler, o que é equivalente, mas ignora a camada HTTP por completo.)
- O handler renderiza apenas os limites de Suspense adiados e envia o resultado por streaming para o `res`.
- Nenhuma ida e volta HTTP é necessária: o handler é invocado no mesmo processo.

### Encontrando rotas com PPR na saída do build \{#finding-ppr-routes-in-build-output}

Na [saída do adapter](/docs/app/api-reference/adapters/output-types), as rotas com PPR são identificadas por `renderingMode: 'PARTIALLY_STATIC'` no array de prerenders. Percorra `outputs.prerenders` para encontrar essas entradas e leia `fallback.postponedState`.

`pprChain.headers` contém os headers necessários para o protocolo de retomada: `{ 'next-resume': '1' }`.

Para uma implementação detalhada com exemplos de código, veja [Implementando PPR em um adapter](/docs/app/api-reference/adapters/implementing-ppr-in-an-adapter).

## Checklist de implementação \{#implementation-checklist}

1. **Leia as saídas do PPR no momento do build.** No `onBuildComplete` do seu adapter, identifique os prerenders com `renderingMode: 'PARTIALLY_STATIC'`. Armazene a casca HTML e o `postponedState` no seu cache.

2. **Sirva a casca no momento da requisição.** Para requisições que chegam a rotas com PPR, sirva a casca em cache imediatamente e comece o streaming.

3. **Retome a renderização dinâmica.** No caso de CDN para origem: envie uma requisição POST ao handler do Next.js com o header `next-resume: 1` e o estado adiado como corpo. No caso de baseado em adapter: chame o handler diretamente com o método POST e o estado adiado no corpo da requisição (ou passe `requestMeta: { postponed: postponedState }` ao handler). Envie a resposta em streaming de volta ao cliente.

4. **Trate as atualizações de cache.** Use `requestMeta.onCacheEntryV2` para capturar novos pares de casca + estado adiado após a revalidação, e atualize seu cache de forma atômica.

5. **Trate a degradação graciosa.** Se o estado adiado estiver indisponível ou desatualizado, volte para uma renderização completa no servidor. O usuário recebe uma página completa, sem a otimização de casca primeiro.

Para a referência completa da API de adapters e exemplos de implementação, veja a [Deployment Adapter API](/docs/app/api-reference/config/next-config-js/adapterPath).
