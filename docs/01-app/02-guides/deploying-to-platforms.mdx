O Next.js [trata conteúdo estático e dinâmico como um espectro](/docs/app/guides/rendering-philosophy) no nível do componente. Diferentes recursos nesse modelo exigem diferentes capacidades da plataforma. Esta página ajuda você a entender o que sua plataforma precisa oferecer e como configurar o seu deploy.

## Requisitos mínimos \{#minimum-requirements}

Para rodar o Next.js, sua plataforma precisa de **um servidor Node.js**. Só isso.

Um único processo `next start` lida corretamente com todos os recursos do Next.js: Server Components, ISR, PPR, Cache Components, Server Actions, Proxy e `after()`. O suporte a streaming é necessário para que recursos como PPR e Server Components entreguem o conteúdo progressivamente (sem ele, as respostas são armazenadas em buffer e enviadas por inteiro, o que ainda funciona, mas perde o ganho de desempenho do streaming). Infraestrutura adicional (cache de CDN, computação na borda, cache compartilhado) melhora principalmente o desempenho e a consistência entre instâncias. Em deployments com várias instâncias, o cache compartilhado e a coordenação de tags reduzem as divergências de conteúdo desatualizado entre instâncias. A única dependência adicional é o pacote `sharp`, que é necessário para a [Otimização de imagens](/docs/app/api-reference/components/image).

## Fidelidade funcional vs. fidelidade de desempenho \{#functional-fidelity-vs-performance-fidelity}

Ao avaliar o suporte de uma plataforma ao Next.js, ajuda distinguir dois níveis:

**Fidelidade funcional** significa que todo recurso do Next.js funciona corretamente. A [suíte de testes de adapters](/docs/app/api-reference/adapters/testing-adapters) é o contrato: se o adapter de uma plataforma passa nos testes, ela tem suporte ao Next.js. É binário: passa ou não passa.

**Fidelidade de desempenho** significa que os recursos alcançam suas características ótimas de desempenho. Exemplos incluem a casca estática do PPR servida com latência de CDN em vez de latência de origem, ou o ISR servindo conteúdo desatualizado instantaneamente com propagação de revalidação em menos de um segundo. A fidelidade de desempenho é um espectro que cada plataforma alcança de um jeito diferente, dependendo da sua arquitetura.

Uma plataforma que alcança fidelidade funcional é um destino de deploy totalmente suportado para o Next.js. A fidelidade de desempenho é o que diferencia as plataformas, e ela melhora de forma incremental com o tempo.

Use a matriz de recursos abaixo com essa lente: "Streaming obrigatório" e "Cache compartilhado recomendado" descrevem o que é necessário para a fidelidade funcional. "Edge Stitching" é uma otimização de fidelidade de desempenho.

## Matriz de suporte a recursos \{#feature-support-matrix}

Diferentes recursos exigem diferentes capacidades de infraestrutura. A coluna "Edge Stitching" é uma **otimização de desempenho**, não um requisito de corretude. Todos os recursos funcionam corretamente a partir de um único servidor de origem.

| Recurso                        | Streaming   | Cache compartilhado | Edge Stitching | Observações                                                                                      |
| ------------------------------ | ----------- | ------------------- | -------------- | ------------------------------------------------------------------------------------------------ |
| Server Components              | Obrigatório | Não                 | Não            | Suporte básico a streaming                                                                       |
| ISR (baseado em tempo)         | Não         | Recomendado         | Não            | Funciona por instância sem cache compartilhado                                                   |
| ISR (sob demanda)              | Não         | Recomendado         | Não            | [Propagação de tags](/docs/app/guides/how-revalidation-works) precisa de cache compartilhado para múltiplas instâncias |
| Partial Prerendering           | Obrigatório | Recomendado         | Opcional       | [Veja o Guia de PPR para plataformas](/docs/app/guides/ppr-platform-guide)                       |
| Cache Components (`use cache`) | Obrigatório | Recomendado         | Não            | O cache compartilhado possibilita consistência entre instâncias                                  |
| Proxy / Middleware             | Não         | Não                 | Não            | Roda na borda ou na origem                                                                       |
| Server Actions                 | Obrigatório | Não                 | Não            | Requisições POST com resposta em streaming                                                       |
| `after()`                      | Não         | Não                 | Não            | Requer suporte a [desligamento gracioso](/docs/app/guides/self-hosting#after)                    |

**Streaming obrigatório** significa que a plataforma precisa oferecer suporte a chunked transfer encoding ou a streaming HTTP/2, e não pode armazenar a resposta em buffer antes de enviá-la ao cliente.

**Cache compartilhado recomendado** significa que várias instâncias do servidor se beneficiam de backends de cache compartilhados para se coordenar. Para ISR e cache de respostas do servidor, use [`cacheHandler`](/docs/app/api-reference/config/next-config-js/incrementalCacheHandlerPath). Para entradas de `'use cache'`, use [`cacheHandlers`](/docs/app/api-reference/config/next-config-js/cacheHandlers). Sem cache compartilhado, cada instância mantém o próprio cache de forma independente: os recursos continuam funcionando corretamente em cada instância, mas os eventos de revalidação não se propagam entre instâncias.

## Compatibilidade de infraestrutura de CDN \{#cdn-infrastructure-compatibility}

A tabela a seguir mapeia as primitivas de infraestrutura de cada CDN principal. São blocos de construção disponíveis, e não integrações prontas:

| CDN               | Computação na borda | Chave-valor / Tags | Armazenamento de blobs | Retomada de PPR |
| ----------------- | ------------------- | ------------------ | ---------------------- | --------------- |
| Cloudflare        | Workers             | KV                 | R2                     | Sim (worker)    |
| Akamai            | EdgeWorkers         | EdgeKV             | Armazenamento de objetos | Sim (worker)  |
| Amazon CloudFront | Lambda@Edge         | KeyValueStore      | S3                     | Sim (Lambda)    |
| Fastly            | Compute             | KV Store           | Armazenamento de objetos | Sim (WASM)    |
| Azure             | Functions           | Redis gerenciado   | Armazenamento de blobs | Sim (servidor)  |
| Google Cloud      | Cloud Run           | Vários KV          | Cloud Storage          | Sim (servidor)  |

Esses são blocos de construção disponíveis, e não integrações finalizadas. A maioria dos adapters da comunidade hoje faz deploy do Next.js como um contêiner Docker ou um servidor Node.js, sem aproveitar primitivas específicas de CDN como KV na borda ou retomada de PPR. Veja a página [Deploy](/docs/app/getting-started/deploying#adapters) para a lista atual de adapters. Para considerações de cache específicas de CDN (incluindo limitações conhecidas com `Vary` em headers personalizados), veja [Cache de CDN](/docs/app/guides/cdn-caching).

## Adapters \{#adapters}

O Next.js oferece uma [API de Deployment Adapter](/docs/app/api-reference/config/next-config-js/adapterPath) que permite às plataformas personalizar como os apps Next.js são construídos e implantados para a infraestrutura delas. Adapters rodam no build e produzem saídas específicas da plataforma a partir do build padrão do Next.js. Qualquer pessoa pode criar um adapter usando a API pública, sem nenhum acesso especial.

A API de adapters somada às interfaces de cache do Next.js forma a superfície completa de integração com a plataforma. O adapter cuida da saída do build, enquanto `cacheHandler` e `cacheHandlers` cobrem caminhos de cache diferentes em runtime. `cacheHandler` (no singular) cobre os caminhos de cache do servidor, como ISR, route handlers, `fetch`/`unstable_cache` com patch e otimização de imagens. `cacheHandlers` (no plural) configura os backends da diretiva `'use cache'`.

### Adapters verificados \{#verified-adapters}

Um **adapter verificado** é aquele que atende a dois requisitos:

1. **Código aberto.** O código-fonte do adapter está disponível publicamente, para que a comunidade e a equipe do Next.js possam inspecioná-lo, contribuir e verificá-lo.
2. **Executa a suíte de testes de compatibilidade.** A plataforma oferece um jeito de rodar a [suíte de testes de compatibilidade do Next.js](/docs/app/api-reference/adapters/testing-adapters) completa contra o adapter dela. Isso dá visibilidade sobre quais recursos funcionam, quais estão em andamento e onde ainda há lacunas.

Adapters verificados ficam hospedados na [organização do Next.js no GitHub](https://github.com/nextjs), são listados como destinos de deploy suportados na documentação do Next.js e são mantidos pelas respectivas equipes das plataformas. Não há hooks privados do framework nem caminhos de integração exclusivos: o adapter da Vercel usa a mesma API pública que qualquer outro adapter.

Para adapters verificados e para plataformas que buscam o status verificado pelo [Ecosystem Working Group](https://nextjs.org/ecosystem-working-group), a equipe do Next.js se compromete com:

- **Testes coordenados.** Antes de grandes releases, trabalhamos com as equipes das plataformas para rodar a suíte de testes de compatibilidade e identificar problemas cedo.
- **Acesso antecipado.** Autores de adapters recebem acesso antecipado a mudanças na API durante RFCs e release candidates.
- **Suporte direto.** Quando o contrato do adapter precisa ser atualizado, trabalhamos diretamente com as equipes dos adapters.

> **Bom saber:** plataformas podem criar adapters de código fechado sobre a mesma API pública e a mesma suíte de testes. No entanto, adapters de código fechado não serão listados como verificados, já que a equipe do Next.js não pode verificar o que não consegue inspecionar.

## Uma observação sobre requisitos de infraestrutura \{#a-note-on-infrastructure-requirements}

O [modelo de renderização](/docs/app/guides/rendering-philosophy) do Next.js coloca a fronteira estática/dinâmica no nível do componente, e não no nível da rota. Fronteiras mais granulares dão mais flexibilidade aos desenvolvedores, ao custo de requisitos mais amplos para as plataformas de hospedagem. É uma troca deliberada: os requisitos de infraestrutura desta página existem por causa do que o modelo de renderização entrega.
