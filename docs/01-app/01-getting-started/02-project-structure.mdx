### Arquivos de roteamento \{#routing-files}

### Rotas aninhadas \{#nested-routes}

Pastas definem segmentos de URL. Aninhar pastas aninha segmentos. Layouts em qualquer nível envolvem seus segmentos filhos. Uma rota se torna pública quando existe um arquivo `page` ou `route`.

| Caminho                     | Padrão de URL   | Observações                   |
| --------------------------- | --------------- | ----------------------------- |
| `app/layout.tsx`            | —               | Layout raiz envolve todas as rotas |
| `app/blog/layout.tsx`       | —               | Envolve `/blog` e seus descendentes |
| `app/page.tsx`              | `/`             | Rota pública                  |
| `app/blog/page.tsx`         | `/blog`         | Rota pública                  |
| `app/blog/authors/page.tsx` | `/blog/authors` | Rota pública                  |

### Rotas dinâmicas \{#dynamic-routes}

Parametrize segmentos com colchetes. Use `[segment]` para um único parâmetro, `[...segment]` para catch‑all e `[[...segment]]` para catch‑all opcional. Acesse os valores pela prop [`params`](/docs/app/api-reference/file-conventions/page#params-optional).

| Caminho                         | Padrão de URL                                                        |
| ------------------------------- | -------------------------------------------------------------------- |
| `app/blog/[slug]/page.tsx`      | `/blog/my-first-post`                                                |
| `app/shop/[...slug]/page.tsx`   | `/shop/clothing`, `/shop/clothing/shirts`                            |
| `app/docs/[[...slug]]/page.tsx` | `/docs`, `/docs/layouts-and-pages`, `/docs/api-reference/use-router` |

### Grupos de rotas e pastas privadas \{#route-groups-and-private-folders}

Organize o código sem alterar as URLs com grupos de rotas [`(group)`](/docs/app/api-reference/file-conventions/route-groups#convention), e posicione arquivos não roteáveis junto ao código com pastas privadas [`_folder`](#private-folders).

| Caminho                         | Padrão de URL | Observações                               |
| ------------------------------- | ------------- | ----------------------------------------- |
| `app/(marketing)/page.tsx`      | `/`           | Grupo omitido da URL                      |
| `app/(shop)/cart/page.tsx`      | `/cart`       | Compartilha layouts dentro de `(shop)`    |
| `app/blog/_components/Post.tsx` | —             | Não roteável; lugar seguro para utilitários de interface |
| `app/blog/_lib/data.ts`         | —             | Não roteável; lugar seguro para utilitários |

### Rotas paralelas e interceptadas \{#parallel-and-intercepted-routes}

Esses recursos se encaixam em padrões de interface específicos, como layouts baseados em slots ou roteamento de modais.

Use `@slot` para slots nomeados renderizados por um layout pai. Use padrões de interceptação para renderizar outra rota dentro do layout atual sem alterar a URL, por exemplo, para mostrar uma visualização de detalhes como modal sobre uma lista.

| Padrão (docs)                                                                               | Significado          | Caso de uso comum                        |
| ------------------------------------------------------------------------------------------- | -------------------- | ---------------------------------------- |
| [`@folder`](/docs/app/api-reference/file-conventions/parallel-routes#slots)                 | Slot nomeado         | Barra lateral + conteúdo principal       |
| [`(.)folder`](/docs/app/api-reference/file-conventions/intercepting-routes#convention)      | Intercepta o mesmo nível | Pré-visualiza uma rota irmã em um modal |
| [`(..)folder`](/docs/app/api-reference/file-conventions/intercepting-routes#convention)     | Intercepta o pai     | Abre um filho do pai como sobreposição   |
| [`(..)(..)folder`](/docs/app/api-reference/file-conventions/intercepting-routes#convention) | Intercepta dois níveis | Sobreposição em um nível muito aninhado |
| [`(...)folder`](/docs/app/api-reference/file-conventions/intercepting-routes#convention)    | Intercepta a partir da raiz | Mostra uma rota qualquer na visualização atual |

## Organizando seu projeto \{#organizing-your-project}

O Next.js **não impõe** uma forma específica de organizar e posicionar os arquivos do projeto. Mas ele oferece alguns recursos para ajudar você a organizá-lo.

### Hierarquia de componentes \{#component-hierarchy}

Os componentes definidos em arquivos especiais são renderizados em uma hierarquia específica:

- `layout.js`
- `template.js`
- `error.js` (error boundary do React)
- `loading.js` (Suspense boundary do React)
- `not-found.js` (error boundary do React para a interface de "não encontrado")
- `page.js` ou `layout.js` aninhado

<Image
  alt="Hierarquia de componentes para as convenções de arquivos"
  srcLight="/docs/light/file-conventions-component-hierarchy.png"
  srcDark="/docs/dark/file-conventions-component-hierarchy.png"

  height="643"
/>

Os componentes são renderizados recursivamente em rotas aninhadas, ou seja, os componentes de um segmento de rota ficam aninhados **dentro** dos componentes do segmento pai.

<Image

### Colocalização \{#colocation}

No diretório `app`, pastas aninhadas definem a estrutura de rotas. Cada pasta representa um segmento de rota mapeado para um segmento correspondente em um caminho de URL.

No entanto, mesmo que a estrutura de rotas seja definida por pastas, uma rota **não fica acessível publicamente** até que um arquivo `page.js` ou `route.js` seja adicionado ao segmento de rota.

<Image
  alt="Diagrama mostrando que uma rota não fica acessível publicamente até que um arquivo page.js ou route.js seja adicionado ao segmento de rota."
  srcLight="/docs/light/project-organization-not-routable.png"
  srcDark="/docs/dark/project-organization-not-routable.png"
  width="1600"
  height="444"
/>

E, mesmo quando uma rota se torna acessível publicamente, apenas o **conteúdo retornado** por `page.js` ou `route.js` é enviado ao cliente.

<Image
  alt="Diagrama mostrando como os arquivos page.js e route.js tornam as rotas publicamente acessíveis."
  srcLight="/docs/light/project-organization-routable.png"
  srcDark="/docs/dark/project-organization-routable.png"
  width="1600"
  height="687"
/>

Isso significa que os **arquivos do projeto** podem ser **colocalizados com segurança** dentro de segmentos de rota no diretório `app` sem se tornarem roteáveis por acidente.

<Image
  alt="Diagrama mostrando que arquivos de projeto colocalizados não são roteáveis, mesmo quando um segmento contém um arquivo page.js ou route.js."
  srcLight="/docs/light/project-organization-colocation.png"
  srcDark="/docs/dark/project-organization-colocation.png"
  width="1600"
  height="1011"
/>

> **Bom saber**: embora você **possa** colocalizar os arquivos do projeto em `app`, não é **obrigatório**. Se preferir, pode [mantê-los fora do diretório `app`](#store-project-files-outside-of-app).

### Pastas privadas \{#private-folders}

Pastas privadas podem ser criadas prefixando uma pasta com um sublinhado: `_folderName`

Isso indica que a pasta é um detalhe de implementação privado e não deve ser considerada pelo sistema de roteamento, excluindo assim **a pasta e todas as suas subpastas** do roteamento.

<Image
  alt="Um exemplo de estrutura de pastas usando pastas privadas"
  srcLight="/docs/light/project-organization-private-folders.png"
  srcDark="/docs/dark/project-organization-private-folders.png"
  width="1600"
  height="849"
/>

Como os arquivos no diretório `app` podem ser [colocalizados com segurança por padrão](#colocation), pastas privadas não são necessárias para a colocalização. No entanto, elas podem ser úteis para:

- Separar a lógica de interface da lógica de roteamento.
- Organizar de forma consistente os arquivos internos em todo o projeto e no ecossistema do Next.js.
- Ordenar e agrupar arquivos em editores de código.
- Evitar possíveis conflitos de nome com futuras convenções de arquivos do Next.js.

> **Bom saber**:
>
> - Embora não seja uma convenção do framework, você também pode considerar marcar como "privados" os arquivos fora de pastas privadas, usando o mesmo padrão de sublinhado.
> - Você pode criar segmentos de URL que começam com sublinhado prefixando o nome da pasta com `%5F` (a forma codificada em URL de um sublinhado): `%5FfolderName`.
> - Se você não usar pastas privadas, vale conhecer as [convenções de arquivos especiais](/docs/app/getting-started/project-structure#routing-files) do Next.js para evitar conflitos de nome inesperados.

### Grupos de rotas \{#route-groups}

Grupos de rotas podem ser criados envolvendo uma pasta em parênteses: `(folderName)`

Isso indica que a pasta serve para organização e **não deve ser incluída** no caminho da URL da rota.

<Image
  alt="Um exemplo de estrutura de pastas usando grupos de rotas"
  srcLight="/docs/light/project-organization-route-groups.png"
  srcDark="/docs/dark/project-organization-route-groups.png"
  width="1600"
  height="849"
/>

Grupos de rotas são úteis para:

- Organizar rotas por seção do site, intenção ou equipe. Por exemplo: páginas de marketing, páginas de administração etc.
- Habilitar layouts aninhados no mesmo nível de segmento de rota:
  - [Criar múltiplos layouts aninhados no mesmo segmento, incluindo múltiplos layouts raiz](#creating-multiple-root-layouts)
  - [Adicionar um layout a um subconjunto de rotas em um segmento comum](#opting-specific-segments-into-a-layout)

### Pasta `src` \{#src-folder}

O Next.js permite armazenar o código do app (incluindo `app`) dentro de uma [pasta `src` opcional](/docs/app/api-reference/file-conventions/src-folder). Isso separa o código do app dos arquivos de configuração do projeto, que geralmente ficam na raiz.

## Exemplos \{#examples}

A seção a seguir lista uma visão geral de alto nível das estratégias comuns. A conclusão mais simples é escolher uma estratégia que funcione para você e sua equipe e mantê-la consistente em todo o projeto.

> **Bom saber**: nos exemplos abaixo, usamos as pastas `components` e `lib` como marcadores genéricos. Os nomes não têm significado especial para o framework, e seus projetos podem usar outras pastas, como `ui`, `utils`, `hooks`, `styles` etc.

### Escolher segmentos específicos para um layout \{#opting-specific-segments-into-a-layout}

Para incluir rotas específicas em um layout, crie um novo grupo de rotas (por exemplo, `(shop)`) e mova para dentro dele as rotas que compartilham o mesmo layout (por exemplo, `account` e `cart`). As rotas fora do grupo não compartilharão o layout (por exemplo, `checkout`).

### Escolher esqueletos de carregamento para uma rota específica \{#opting-for-loading-skeletons-on-a-specific-route}

Para aplicar um [esqueleto de carregamento](/docs/app/api-reference/file-conventions/loading) por meio de um arquivo `loading.js` a uma rota específica, crie um novo grupo de rotas (por exemplo, `/(overview)`) e depois mova seu `loading.tsx` para dentro desse grupo.

<Image
  alt="Estrutura de pastas mostrando um loading.tsx e um page.tsx dentro do grupo de rotas"
  srcLight="/docs/light/route-group-loading.png"
  srcDark="/docs/dark/route-group-loading.png"
  width="1600"
  height="444"
/>

Agora, o arquivo `loading.tsx` se aplica apenas à página de visão geral do dashboard, em vez de todas as páginas do dashboard, sem afetar a estrutura do caminho da URL.

### Criar múltiplos layouts raiz \{#creating-multiple-root-layouts}

Para criar múltiplos [layouts raiz](/docs/app/api-reference/file-conventions/layout#root-layout), remova o arquivo `layout.js` de nível superior e adicione um arquivo `layout.js` dentro de cada grupo de rotas. Isso é útil para dividir um app em seções com interface ou experiência completamente diferentes. Você precisa adicionar as tags `<html>` e `<body>` a cada layout raiz.

<Image
  alt="Grupos de rotas com múltiplos layouts raiz"

  srcDark="/docs/dark/route-group-multiple-root-layouts.png"
  width="1600"
  height="687"
/>

No exemplo acima, `(marketing)` e `(shop)` têm, cada um, seu próprio layout raiz.
